「読書メモは効くがコストが高すぎる」「地図と参考文献でよいのでは」は関心ではなく**やる夫の仮説**として扱う。
A・Cの第1幕で本人に宣言させ、本編で検証・修正する対象に置く。
メモのコスト仮説はA第5幕で判定する。地図と参考文献仮説はA第7幕とC第7幕の両方で判定するが、Aは「頭に残す塊」の側から、Cは「外部化の設計」の側から判定し、結論の言い方を変える。

## 全案に共通する仕掛け

- 生徒はやる夫、教師はやらない夫。**やらない夫は現実世界では普通の友人・同僚として登場し、夢の中でだけ偉人や研究者の姿を借りる。**
- 各幕（または各節）に対応する研究者を1人割り当てる。姿は借りるが、**史実にない発言・逸話・数値を作らない。** 台詞はあくまでやらない夫のものとして書き、実験手順・被験者条件・結果の方向だけを史実に依拠させる。人物が特定できない主張は、人名を出さず現象として書く。
- 夢から覚めた現実側の場面を各幕の最後か次幕の冒頭に置き、夢で得た道具をやる夫が自分の生活（積んだ新書、居酒屋、通勤電車、仕事）で試す。夢だけで完結させない。
- 覚醒／入眠の描写を毎回同じ文型で書かない。眠りに落ちる契機（本を読みながら、電車で、深夜のメモ作業中）を変える。

## 執筆セッションの進め方

1. `yaruo-rediscovery` スキルを起動し、指示どおり `references/final-checklist.md` を全文読む。
2. 担当の `plan-*.md` の Step 0・幕構成・核心概念表をそのまま制作計画として採用する。**企画書の幕構成はユーザーへ提示して合意を取る**（案の採用自体は合意済みなので、確認は幕構成と概念表の粒度に絞ってよい）。
3. 「執筆前に検証する事実」の各行を先に確認し、URLを作業メモへ残す。`未検証` の行を確認せずに本文へ書かない。数値が違っていたら本文の反例設計から直す。
4. 2幕書いたら止めてユーザーのレビューを受ける。以降も同じ刻みで進める。
5. 完成後：`python3 scripts/check_dialogue_constraints.py docs/books/<slug>/README.md` → `yaruo-format` → `yaruo-proofread` → `python3 scripts/generate_site.py`。
6. `docs/catalog.yaml` への登録は、本文完成をユーザーが確認した後に行う。登録案は各企画書の末尾にある。
7. `git add docs/` でコミットする。`build/` は絶対に含めない。案ごとに別ブランチを使う（`claude/book-<slug>` を推奨）。

## 既刊との重複回避

- `life-meaning`（才能・生存者バイアス・地位財）と `merit-and-luck`（才能の帰属）が近い。**才能の有無や努力の道徳的評価はどの案でも主題にしない。** 扱うのは「知識と記憶がどう作られ、どう使われるか」に限る。
- Dは既刊2冊といちばん近い。生存者バイアスと天才の話は、才能論ではなく**知識の集団的蓄積**の文脈だけで扱う。
- `mathematical-foundations`（命題・形式体系）とVIIが接する。DのJTBやゲティアは形式論理へ踏み込まず、認識論の水準で止める。
- `rental-car-operations`（業務設計）と `payroll-calculation`（例外と引き渡し）がCの第7幕と接する。Cは業務手順ではなく**業務知識の表現形**に限定する。
