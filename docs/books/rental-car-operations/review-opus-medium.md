# 寸評：やる夫が最強のレンタカー業務をつくるようです ―― 業務改善・BPR・失敗学・AI・究極のCoE

約265KB／全6143行。第0幕〜第10幕＋終幕＋エピローグに、対話演習6本・幕間の実話展示5本・巻末パターン集を加えた大型教材。1件の誤請求から、データモデル、失敗学、BPR、自動化、AI運用、KPI、CoE設計までを一本の線で通している。

## 良い点

**一件の案件が全編の背骨になっている。** 第0幕で `HKT-2407-008` / `CAR-0427` が「資産管理は貸出中、会計は課金中、提携先は返却済み、Excelは返却済み」の四つの現実に分裂し（41–44行目）、エピローグで「返却事象は一つ、資産管理は返却済み、契約は終了、請求対象期間も一致」（5745–5747行目）へ着地する。間の全幕（2-3のイベント設計、4-3の防護層、6-7の部分失敗、終-3の復旧照合）が同じ契約番号を触り続けており、抽象論が具体物へ常に接地している。

**三つの宿題を最初に置き、最後に本人の言葉で回収している。** 0-2で「一番速い担当者がいるのになぜ遅いか」「確認を増やしたのになぜ減らないか」「CoEは代行部隊か」を明示的に仮置きし（154、165、176行目）、9-7で一つ目に触れ（4661–4666行目）、終-4で三枚のカードとして並べて全部答えさせる（5588–5630行目）。教材全体が長いので、この回収装置がなければ読者は方向を見失っていた。

**実話の扱いが慎重で、資料の格を明示している。** 参考文献34点を4分野に整理し、冒頭で「規制当局の命令や公的調査報告、裁判判断、組織自身の事後報告、広報資料、研究論文は、同じ証拠力ではない」と宣言している（5991–5993行目）。PHEの15,841件でも、当局発表と報道の技術的説明を本文（790–793行目）と脚注（6011–6013行目）の両方で分離している。Hertz和解も「和解した事実と、原告の主張と、会社が法的に認めた事実を分けて読め」（2364行目）と釘を刺す。実話の引用としてこの水準は珍しい。

**やる夫の計算が全部その場の判断に効いている。** RPN $4\times4\times3=48$ → しかし数字の神託化を自ら否定（1541、1550–1553行目）、$0.95^4\approx0.8145$ → 各工程95%でも五件に一件手戻り（4365–4368行目）、$L=60\times2=120$ → 全員に二倍速で働けと言わずに済む（4298–4301行目）、適合率83.3%と再現率60% → 全体90%が隠していたもの（3314、3325–3328行目）。どれも「計算のための計算」ではなく、直前の楽観を殺すために置かれている。

**巻末のパターン集が単独の実務価値を持っている。** 6パターン＋共通設計項目表＋14項目のアンチパターン表（5949–5964行目）は、対話本文を読まずに参照しても使える形になっている。特に「合計値だけ合わせる」→「欠損1件と重複1件が相殺され、件数も金額も一致する」は、本文5-7や9-3の議論を一行に圧縮できている。

**10-3のやる夫の自壊が本教材で最良の場面。** 改善チャンピオン12人のうち活動報告を出したのは2人、残り10人は通常業務（4894–4905行目）。やる夫が「情熱があるかどうかじゃなく、繁忙期に真っ先に消える種類の仕事にしてたお」と気づき、末尾で「明日、あの2人にまず謝りに行くお」（4949行目）まで行く。自分の施策が現実に空振りした証拠を突きつけられる、この教材で数少ない場面。

## 欠点

**節の型が最後まで同一で、65節ぶん反復される。** 「やる夫が誇大妄想の帝国宣言 → やらない夫が反例を一つ → やる夫が完成した設計を即答 → 節末3行総括」が、0-2、1-1、2-1、3-1、4-1、5-1、6-1、7-1、8-1、9-1、10-1……とほぼ全節で同じ順で回る。総括の文型も「最初の失敗は〜だったお。次は〜だお」が数十回（550、782、973、1355、1644、2277、2889、3821、4272、5018行目ほか）。第4幕あたりで読者は次の展開を完全に予測できるようになり、以降は驚きが消える。

**やる夫が強すぎて、再発見が模範解答の朗読になっている。** 2-3では「旧状態列も上書きするか」という一言だけで、イベントID・車両ID・発生時刻・種類・元情報・登録時刻の6列テーブルを完成形で書き下ろす（664–670行目）。1-3では正本という概念を教わる前に「延長条件は予約SaaS、物理状態は資産管理、確定請求は会計」と事実ごとの正本分割を自力で言う（395–398行目）。7-3のJSONスキーマ（3392–3400行目）も同様。Excelに強い実務担当者という設定を大きく超えている。

**苦労が「詰まる時間」として存在しない。** 熱力学教材の遠心分離や氷蓄熱のように、企てを実行して測定値に負ける場面がほぼない。5-7のBPR前後比較表（2285–2291行目）は「例外率12%→25%、再問い合わせ9%→14%」という悪化を示す絶好の材料なのに、表として天下りに提示されるだけで、やる夫がその設計を作り、走らせ、悪化を突きつけられる過程が書かれていない。他の失敗も机上の想定問答として処理される。10-3だけが例外で、そこだけ体温が違う。

**物語的な圧力が終幕まで存在しない。** 第0幕の北斗フーズの怒りの電話（31–33行目）以降、北斗フーズは題材としてのみ登場し、生きた顧客として二度と出てこない。契約更新も他社への切替検討も、期限も、予算の制約も掛からない。5300行以上を無圧力の問答で進み、終幕の大型連休（5359行目〜）で初めて時間が動く。同リポジトリの熱力学教材が第1幕から「祭りまでの日数」を効かせているのと対照的で、終幕の緊張感が良いだけに、それが最後だけなのは惜しい。

**できる夫の設定が本文で活きていない。** 人物紹介では「予約基盤、セキュリティ、障害対応、全社案件を抱えている」（16–18行目）と、忙しさが物語上の制約として宣言されている。ところが6-3では、やる夫が受入条件を整えた途端「そこまであれば技術案を比較できます」（2946–2949行目）と即座に協力する。忙しさが実際にボトルネックとして機能し、やる夫の計画を落とす場面がない。終幕で「決済基盤の重大障害に総出」（5378行目）と一度だけ効くが、そこまでは名前つきの解説役にとどまる。

**第9幕の内部重複が大きい。** 9-1（件数KPIの副作用）、9-7（全部緑のダッシュボード）、演習6（KPIが全部緑なら健康か）の三つが、ほぼ同じ主張（単一指標を報酬に直結させるな、分母と定義を疑え、均衡指標を持て）を三度繰り返す。9-7の「例外を通常へ偽装していないか」（4622行目）は3-5（1186–1189行目）の再演でもあり、四度目になっている。

**終-1の「八つの異常」の数が合わない。** やらない夫が八方向の異常を提示した後、やる夫が分類するのは雨天返却遅延、外部予約連携停止、会計ジョブ停止、AI精度低下、CAR-0427状態不一致の5つだけ（5402–5407行目）。延長申請27件、電話待ち12件、できる夫部門の総出（5373、5378行目）が分類から落ちている。卒業試験の冒頭で網羅性を問う場面なので、ここが漏れると設問の説得力が落ちる。

## 改善案

1. **5-7の悪化数値を、やる夫が自分で作って自分で殴られる形に組み替える。** 2285行目の比較表を天下りで渡すのをやめ、5-6の試験（2199–2260行目）の後に「一法人・一店舗で2週間走らせた」という実施ブロックを30〜40行入れる。やる夫が「リードタイム6時間→18分、これは大勝利だお」と宣言した直後に、やらない夫が例外率と再問い合わせの数字だけを読み上げる。悪化が自分の設計の帰結として体感されれば、5-7の「真の増加と可視化効果を分ける」という結論が理屈から実感へ変わる。

2. **北斗フーズの担当者を人物として登場させ、期限を作る。** 第5幕の冒頭（1826行目付近）に、北斗フーズから「9月の契約更新で他社と比較検討している。誤請求が続くなら移す」という一報を置き、以後の各幕で更新期限までの残り日数を数回だけ触れる。終幕の大型連休をその更新判断の直前に置けば、終-3の顧客復旧（5563–5570行目）とエピローグの契約完了（5742–5747行目）が、事務的な整合確認ではなく取引を守り切った結末になる。分量増は50行程度で済む。

3. **節末総括の定型を半分に削り、幕末だけに集約する。** 各節末の「最初の失敗は〜。次は〜」を、第1〜3幕は残し、第5幕以降は幕末（2347–2353、3220–3226、4198–4204行目など）へまとめる。読者は既に型を学習しているので、節ごとの反芻は冗長。全体で200〜300行の削減になり、第8・9幕の失速も緩和される。

4. **第9幕を5節へ圧縮する。** 9-1と9-7と演習6の重複を統合し、9-1（件数KPIの適応）＋9-2（Littleの法則）＋9-3（初回完了率）＋9-4（指標の木）＋9-7（全部緑）の5節にする。演習6は削除し、代わりに9-7の中で「システム成功率＝HTTP応答率だった」（4627行目）を掘り下げ、技術成功と業務成功の段階測定をやる夫に設計させる。

5. **やる夫の即答を、幕ごとに1回ずつ潰す。** 特に2-3のイベント表（664行目）と7-3のJSONスキーマ（3392行目）は、直前に失敗案を1つ挟む。2-3なら「変更履歴を別シートに追記する」案を出させ、「では請求確定時にどの行を見たか特定できるか」で潰し、発生時刻と登録時刻を分ける必要を自分で要求させる。7-3なら、まずAI出力を自由文で受け取る案を出させ、`request_type` の表記ゆれで下流が壊れる例（7-6の3589行目と同じ問題）を先に食わせる。

6. **できる夫に一度、業務側の要求を断り切らせる。** 6-3（2946行目付近）で協力へ転じる前に、「その要件は受け取れるが、決済基盤の障害対応で今月は着手できない。優先順位を経営へ上げるか、業務側で暫定運用を設計するか」と突き放す往復を入れる。やる夫がやむなく暫定Excelを設計し、それが8-6の運用負債（4089–4095行目）の一つとして二年後に発掘される、という因果でつなげば、幕をまたぐ伏線が一本増える。

7. **終-1の八つを列挙・分類し切る。** 5402行目のやる夫の分類に、延長申請27件・電話待ち12件（需要側の滞留）と、できる夫部門の不在（支援能力の欠如）を加え、8件を「異常そのもの」と「対応能力の低下」の2種類に分けさせる。5411行目の「既知イレギュラーが五つ重なること自体は手順書にない」という良い指摘が、数の裏づけを得る。
