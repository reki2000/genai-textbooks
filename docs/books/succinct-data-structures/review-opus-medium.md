# 寸評：やる夫が1ビットも無駄にできないようです ── 簡潔データ構造を再発見する

約75KB／全9幕。512MBの防災端末に1億件を載せるという制約から出発し、rank/select・Elias–Fano・LOUDS・Wavelet Matrix・FM-index・RRRを順に組み、最後に「簡潔化が目的ではない」へ着地する。

## 良い点

**「ビット予算メーター」が計測器として全幕を貫く。** 14行目で人物表に登録され、188–192行目で「推定使用量18.7GB、予算超過率3652%、起動可能性なし」、502–506行目で「警告、索引が本体の32倍です」、664–668行目で初めて予算内、2719–2726行目で最終判定。抽象的な容量議論が、常に一つのメーターの針として可視化される。1163–1177行目で評価項目が容量から演算・応答時間へ拡張されるのも良く、計測器自体が教材とともに成長する。

**3枚の演算カードが本当に全構造を貫通する。** 382–404行目で access / rank / select を導入し、LOUDS の親子移動（1336–1350行目）、Wavelet Matrix の区間写像（1585–1607行目）、FM-index の後方検索（1970–1985行目）まで全部これに帰着する。2600–2610行目で「別々に見えた構造が、同じ基本演算でつながっていたお」と明示的に回収される。

**「大区画＋小区画＋短い残り」が3回反復され、やる夫が反復に気づく。** 2-1のrank（645行目）、4-2の括弧列で「また同じ構図だお」（1449–1450行目）、7-1のRRRで「また、大区画＋小区画＋短い残り」（2162–2172行目）。設計パターンとしての学習が、明示的な自己認識を伴って起きる。

**できる子の実測が理論を3回裏切る。** 3-2で差分可変長2.11MiB＜Elias–Fano 3.28MiB なのにアクセスは4.8ms対41ns（1141–1157行目）。5-2でWavelet Treeが容量には入ったが83msで要件未達（1652–1663行目）。7-2でRRRが2〜4倍遅い（2201–2212行目）。「小さい＝良い」という素朴な信念が、毎回測定値で潰される。

**8-2の結論が最小容量を選ばない。** 2431–2439行目、圧縮中心版403MiBではなく、ハイブリッド版458MiBが要件を満たす。しかも2444–2456行目で「どこをPlainへ戻し、どこを圧縮したか」を具体的に述べさせる。理論最小が答えではない、という主題が数字で決着する。

**9-2の過剰最適化の反転。** 2615–2620行目でやる夫が「社員100人の名簿もLOUDSとFM-indexにするお」と暴走し、2623–2639行目で潰される。学んだ直後に適用条件を自分で列挙させる（2644–2673行目）構成は、道具を渡して終わりにしない。

**締めのオチに伏線がある。** 2746行目「境界条件の1ビットまで削るなよ」→2749行目「`rank` の定義が1ずれて全検索が壊れたお！！」。802–809行目で「1ビットを削る話なのに、1のずれで全部壊れるお」と既に置かれている。

**参考文献10点がすべて原論文または標準教科書で、対応箇所つき。** Jacobson 1989、Raman–Raman–Rao 2002、Elias 1974、Fano 1971、Okanohara–Sadakane 2007、Grossi–Gupta–Vitter 2003、Claude–Navarro–Ordóñez 2015、Burrows–Wheeler 1994、Ferragina–Manzini 2000、Navarro 2016（2763–2781行目）。リポジトリ内で最も充実した文献リスト。

## 欠点

**1908–1910行目のBWTの $F$ が誤っている。** 1877–1885行目の巡回文字列は7行あり、各行の先頭文字を並べると `$aaabnn`（7文字）になる。ところが本文は $F=\texttt{aaabnn}$（6文字）と書き、終端記号 `$` を落としている。これは1927–1931行目の $LF(i)=C[c]+\operatorname{rank}_c(L,i)$ で使う「$c$ より小さい文字の総数 $C[c]$」の理解に直結する箇所で、`$` が最小の文字だという1801行目の設定とも矛盾する。

**カタラン数の添字が途中でずれる。** 1220–1221行目で $n$ ノードの順序木の総数を $C_{n-1}$ と正しく書いた後、1233行目と1239行目では $C_n$ の漸近形を使い、そのまま「1ノードあたり約2ビット」と結論する。結論自体は正しいが、$C_{n-1}$ と $C_n$ が混在したまま計算が進む。

**やる夫が自分で反例に気づく場面がほとんどない。** 素朴案はやる夫が出すが、潰すのは常にやらない夫の質問（「容量は？」「$n$ を大きくしたとき？」）かできる子の測定値。全2782行で、やる夫が誰にも促されず自分の案の欠陥を言うのは1149–1150行目と2445–2447行目程度。第5幕以降は「作る→測られる→遅い／大きい」の型が4回続き（3-2・5-2・7-2・8-2）、後半は結果が予測できてしまう。

**第9幕の現場試験が全問成功で終わる。** 2480–2482行目で台風接近とネットワーク切断という緊張が設定されるのに、2490–2586行目の5つの問い合わせはすべて要件内で通過する。しかも8-2で「99パーセンタイル43ms」と既に判明しているため、結果に不確実性がない。物語のクライマックスが、確認作業になっている。

**総括リストが4箇所に分散して重複する。** 1768–1777行目（可能な問い合わせ）、2411–2429行目（評価項目）、2644–2673行目（適用条件と不要条件）、2681–2691行目（構造の選択表）。役割が近く、第7幕以降は新概念が減る一方でリスト形式の整理が積み重なる。

**できる夫の造形が単調。** 2255–2262・2392–2400・2431–2436行目、いずれも「！」で数値を読み上げる役。2268行目の「競技が違います！」が唯一の見せ場で、他は測定結果の出力装置になっている。

## 改善案

1. **1908–1910行目の $F$ を `$aaabnn` に修正する。** 7行の表と文字数を一致させる。あわせて1917行目の「$L$ の1番目の `a`……」の説明で、`$` の行がどう対応するかを一言添えると、$C[\texttt{a}]=1$ という値が読者に立つ。

2. **カタラン数の添字を統一する。** 1220行目で $n$ ノードの木を $C_{n-1}$ 通りとした規約を保ち、1233・1239行目を $\log_2 C_{n-1} \approx 2n - \frac32\log_2 n + O(1)$ と書き直す。あるいは冒頭で $C_n$ を「$n$ ノードの順序木の総数」と定義し直して全体を揃える。

3. **やる夫に自分で潰させる場面を2つ作る。** 2-1で累積和が400MBになった直後（499行目）、メーターの警告を待たずに「本体12.5MBなのに索引が400MB、これは索引じゃなくて本体だお」と言わせる。5-1で値ごとのビットベクトル案を出した直後（1536行目）、やらない夫の「値域は？」を待たずに、自治体コードが数千種あることを自分で思い出して潰させる。素朴案の提出者と棄却者が同一になる回が増えれば、後半の型の固定が緩む。

4. **第9幕に1件だけ失敗を入れる。** 5つの問い合わせのうち全文locate（2579–2583行目）が最初52msで要件を超え、接尾辞配列の標本間隔を粗くしすぎたことに気づいて調整する往復を置く。8-2で「99パーセンタイル43ms」と示された後だからこそ、テール側の1件が落ちる展開が自然で、2030行目の「標本間隔と復元コストの綱引き」が実地で効く。

5. **総括リストを2つに畳む。** 1768–1777行目は第5幕末の短い確認として3行程度に縮め、2644–2673行目の条件列挙と2681–2691行目の選択表を1つの表に統合する（各行に「有力な構造／条件／不要になる場合」の3列）。第7幕以降の冗長感が減り、2694–2699行目の一文要約が締めとして立つ。

6. **できる夫に一度だけ判断させる。** 2431–2436行目で結果を読み上げた後、「圧縮中心版を推します！ 最小です！」と主張させ、やる夫が2439行目で反論する形にする。数値の出力装置から、誤った推薦をする役へ一度だけ転じさせれば、8-2の結論（最小容量が答えではない）が対話として成立する。

7. ビット予算メーターはビットくんという名前にする。
