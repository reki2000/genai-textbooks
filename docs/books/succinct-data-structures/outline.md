# やる夫が1ビットも無駄にできないようです ── 簡潔データ構造を再発見する の骨格

枠組みは全国防災情報検索システム（**地点1億件、メモリ512MB、検索50ms以内、ネットワーク切断時も動作**）。**ビットくん**という計測器が各幕で使用量と判定を読み上げ、終幕で最終表示を出す。**3枚の演算カード**（`access` / `rank` / `select`）が全編を貫く。

## 第1幕　512MBしかない
- 1-1　ポインタ木・オブジェクト配列・ハッシュ表・転置インデックスで端末が再起動。1件8バイトの無駄が1億件で800MBになる。メモリ増設も端末数万台の制約で不可。「実装が要求する容量」と「本質的に必要なビット数」の区別（避難所フラグ1ビットを1バイトで持っている）。ビットくん誕生、初回表示は18.7GB・超過率3652%。
- 1-2　16地点の「やる市」を導入（以後の縮小例）。任意ビット列なら16ビット、1が5個と分かっていれば $\log_2\binom{16}{5}\approx12.09$ ビット。1億件・避難所1%なら $H_0(0.01)\approx0.0808$ で約1MB対、素朴なビット列12.5MB、バイト配列100MB。小型化／圧縮データ構造／簡潔データ構造の用語区別、$\text{下限}+o(n)$ という目標、そして**3枚の演算カード**を作る。

## 第2幕　数えたいが、数え表は置けない
- 2-1　`rank` の実装。全累積和は400MBで「索引のほうが本体」（やる夫が自分で先に潰す）。100件ごとの標本＋`popcount` は実用的だが漸近的に $O(n\log n)$。二階建て（スーパーブロック $(\log n)^2$ ／ブロック $\frac12\log n$ ／残りは1ワード）で $o(n)$ を達成。**「大区画＋小区画＋短い残り」**という定型が確立し、以後 4-2・7-1 で繰り返される。ビットくんが初めて緑になる。
- 2-2　`select`。位置配列は密なビット列で169MBになる。`rank` の単調性から二分探索 $O(\log n)$、さらに1の個数ごとの標本と、疎な区間／密な区間で処理を変える設計。`rank_0(i)=i-rank_1(i)`。**0始まり／1始まりの境界条件で式が1ずれる危険**を明示（終幕の落ちで回収）。

## 第3幕　増加列を整数のまま持たない
- 3-1　昇順の地点ID列。64ビット配列→6ビット→差分＋可変長（ランダムアクセスが遅い）→上位/下位分割へ。$L=\lfloor\log_2(U/m)\rfloor$、上位値 $h_i$ を位置 $h_i+i$ の1へ変換すると $h_i=\operatorname{select}_1(i)-i$ で復元できる＝Elias–Fano。整数列のランダムアクセスがビット列の `select` に変わる。
- 3-2　容量 $m(\log_2(U/m)+2)$ の見積り、100万件・値域 $2^{40}$ で8MB→2.75MB。向く用途（転置インデックス、時刻、メッシュID、隣接先）と向かない条件（非単調、密、更新）。**できる子の実測で差分可変長のほうが小さい（2.11MiB対3.28MiB）が、100万番目の取得は4.8ms対41ns**という逆転を見せ、「容量だけで選ぶと危険」。ビットくんに演算と応答時間の項目を追加。

## 第4幕　木からポインタを追放する
- 4-1　1ノード24バイトのポインタ木に対し、順序木の種類数はカタラン数で $\log_2 C_{n-1}\approx 2n-\frac32\log_2 n$＝1ノード約2ビット（実装は約100倍）。8ノードの住所木（日本／東京都・大阪府／…）を幅優先で並べ、各ノードの次数を $1^d0$ で連結して $2n-1=15$ ビット＝**LOUDS**。親子移動は `select_0` と `rank` に帰着。「ポインタは関係そのものでなく、関係先のアドレスを直接記録した冗長な案内板」。
- 4-2　部分木の列挙には幅優先が不向き→深さ優先の括弧列（$2n$ ビット）。`excess(i)=rank_1(i)-rank_0(i)`、対応括弧・親・部分木サイズ $(q-p+1)/2$。区間最小値の補助索引もまた「大区画＋小区画＋短い残り」。LOUDS（幅優先・トライ）と平衡括弧（深さ優先・祖先/部分木）の使い分け。実測で住所木1842万ノードが702MiB→5.1MiB。

## 第5幕　数値列を縦に切る
- 5-1　値ごとにビットベクトルを作る案を、**やる夫が自分で潰す**（自治体コード3000種で250倍、収容人数は値域数万、しかも空の列が2900本）。最上位ビットから値域を二分する＝Wavelet Tree。区間写像 $[l,r)\to[\operatorname{rank}_b(l),\operatorname{rank}_b(r))$、範囲頻度と $k$ 番目に小さい値の求め方。
- 5-2　ノードオブジェクトで実装してポインタを復活させ、L3ミス28%・範囲分位点83msで50ms要件を落とす。階層ごとに0を前半・1を後半へ安定的に並べ替え、$Z_d$ を記録する**Wavelet Matrix**へ。ポインタ不要、実測で38MiB減・21ms・ミス率9%。「計算量だけでは性能は決まらない、局所性が支配的なことがある」。

## 第6幕　全文を保存せず全文検索する
- 6-1　`banana$` で接尾辞配列を作り、64ビットで10GBのテキストに80GBかかることを確認。BWT列 $L=\texttt{annb\$aa}$、$F=\texttt{\$aaabnn}$。**やる夫が `$` を落としかけて $C[\texttt{a}]$ が1ずれると自分で気づく**（1ビット教材で1文字落とす自己言及）。LF写像 $LF(i)=C[c]+\operatorname{rank}_c(L,i)$。
- 6-2　後方検索。$l'=C[c]+\operatorname{rank}_c(L,l)$、$r'=C[c]+\operatorname{rank}_c(L,r)$ で `ana` の区間が $[0,7)\to[1,4)\to[5,7)\to[2,4)$。大きなアルファベットの `rank` は 5幕のWavelet Matrixで実装＝FM-index。位置復元には接尾辞配列の標本が必要で、**標本間隔 $s$ と復元コスト $O(s)$ の綱引き**（9-1 で回収される最重要の伏線）。自己索引。実測で原文3.8GiB・接尾辞配列21.6GiB→FM-index全体487MiB。

## 第7幕　1ビットなら小さいという油断
- 7-1　1%しか1がないビット列は理論下限0.0808ビット/要素。ブロックを（クラス $k$、オフセット）で表す**RRR**。ここでも「大区画＋小区画＋短い残り」。$nH_0(B)+o(n)$。
- 7-2　全部RRRにしたら2〜4倍遅くなる（LOUDS親子移動18ns→73ns、範囲頻度11ms→26ms）。Plain / RRR / Elias–Fano / Roaring の4候補を、容量と必要演算で比較。できる夫のベンチマークに対し「どれが勝者か」→**「競技が違います」**（8-2 で2回目が出る）。ビットくんに分布（1の比率・値域・単調性・繰り返し・更新頻度）を追加。

## 第8幕　簡潔でも更新できない
- 8-1　途中への1件挿入で位置がすべて動く。動的ビットベクトルはポインタと局所性の悪化を招く。**静的な基礎層＋小さな更新差分層＋閾値到達時の再構築**（LSM-tree的階層化）へ。
- 8-2　5方式の最終性能試験。できる夫が最小容量の圧縮中心版（403MiB）を推薦するが、**やる夫が「要件は中央値でなく50ms以内」「一部のlocateで88ms」と指摘して却下**し、ハイブリッド版（458MiB、99%tile 43ms）を選ぶ。「55MiBの余白は無駄でなく、更新できない構造が生きるための余白」。どこをPlainに戻し（Wavelet Matrix上位階層）どこを圧縮したかを説明し、**このとき接尾辞配列の標本間隔を32→64へ粗くして2MiB削る**（9-1 の伏線）。cold cacheでは圧縮が速い場合もある。

## 第9幕　1ビットを削る理由
- 9-1　台風下の現場試験（ネットワーク切断、461MiB使用）。`rank`（給水所数0.04ms）、`select`（20番目の避難所0.11ms）、LOUDS（町域列挙0.3ms）、Wavelet Matrix（範囲分位点7.8ms）、FM-indexのcount（1.9ms）と続き、**最後のlocateだけが52msで落ちる**。原因は 8-2 で自分が粗くした標本間隔で、「6-2で自分が書いた綱引きで自分が負けた」「countしかしない検索は速いままなので中央値では見えず、locateする1%だけが遅い」と診断。32へ戻して2MiB増（463MiB）で18msに。「2MiBで34ms買えた」「最小容量を選ばないと口で言うのと、測定値を見てから2MiB差し出すのは別の技能」。3枚の演算カードが全構造を貫いていたことを確認。
- 9-2　「今後すべてを簡潔構造で」という過剰最適化を、社員100人の組織図で潰す。9行の選択表（課題／有力な構造／使う条件／使わない条件）を作り、**表全体が無効になる条件＝規模**（数千万〜数十億要素、1要素数バイトの差がシステムの可否を変えること）を明示。簡潔データ構造の一文定義。ビットくんの最終表示（463MiB／99%tile 24ms／運用可能）。落ちは `rank` の定義が1ずれて全検索が壊れる＝2-2 の境界条件の回収。

## 依存
- **3枚の演算カード**（1-2 で作成）は 2幕（ビット列）→3幕（Elias–Fano の `select`）→4幕（LOUDSの親子）→5幕（Wavelet Matrixの区間写像）→6幕（FM-indexの後方検索）→9-1（全部が同じ演算だったと総括）で一貫して使われる。カードを増減すると全編と 9-1 の総括が連動する。
- **「大区画＋小区画＋短い残り」**は 2-1 で確立し、4-2（区間最小値）と 7-1（RRRのrank）で明示的に反復される。本文が「また同じ構図」と言う箇所。
- **境界条件の1ずれ**は 2-2（rank/selectの0始まり1始まり）→6-1（$F$ から `$` を落としかける）→9-2 の落ち、の3回で反復するテーマ。
- **接尾辞配列の標本間隔**は 6-2 で「綱引き」として提示 → 8-2 で32→64へ粗くして2MiB削る → 9-1 で52msの原因として露見し32へ戻す、という3段構えの本編最大の伏線。8-2 の削減を消すと 9-1 の山場が成立しない。
- **「競技が違います」**は 7-2 と 8-2 の2回。8-2 では「2回目だお」と本文が数えている。
- できる夫が最小容量を推薦して要件を落とす構造（8-2）は、7-2 のベンチマーク提示と対をなす。
- やる夫が自分で素朴案を潰す場面が 2-1（索引のほうが本体）、5-1（値ごとのビット列が3000本）、6-1（`$` を落とすと1ずれる）の3箇所にあり、いずれも「今日はやる夫が先に潰す」と自己言及している。
- ビットくんの表示は 1-1（18.7GB）→2-1（400MBの警告）→2-1末（初の緑）→9-2（最終表示463MiB）と進む。数値を変えるなら全箇所。
- やる市（16地点、$B=0010100110010100$）は 1-2・2-1・2-2・4-1 で使い回す縮小例。ビット列を変えると `rank_1(10)=4`、1の位置 `2,4,7,8,11,13`、図2-1 が連動する。
- 図は5枚：fig `rank-two-level`（2-1）、`elias-fano-transform`（3-1）、`louds-encoding`（4-1）、`wavelet-matrix-range`（5-2）、`fm-backward-search`（6-2）、`static-delta-hybrid`（8-1）。該当節の縮小例を変えたら `scripts/figs/succinct-data-structures.py` も直す。
- 注意：5-1 に**やらない夫の台詞が2回連続で重複している**箇所がある（「値を2進数で見ろ。$\sigma=8$ なら…」が2つ続く）。修正するならこの重複を消す。
