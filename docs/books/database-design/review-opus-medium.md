# 寸評：やる夫で学ぶデータベース設計 ── 給与計算システムを再発明する

約99KB／全8幕。給与システムの設計を通じて、正規化の外側にある「関係の自由度・時間・同一性」の三原則を、素朴案を反例で潰しながら再発見する教材。

## 良い点

**第1幕の3件の連絡が、全8幕の設計図として機能している。** 兼務・遡及昇給・再入社という業務連絡（114–122行目）が、そのまま三大難所（152–154行目）に一対一対応し、それぞれ第2幕・第3幕・第6幕で回収される。しかも「正規化は文法だ。どんな文を書くべきかは教えてくれない」（148行目）という主題の宣言が、やる夫自身の「決めた属性に対して、だお」（141行目）という気づきから出ている。導入部の設計として非常に効率が良い。

**反例が実行結果で決着する。** 浮動小数点の 0.9999999999999999（79–84行目）、JSONBキーの表記ゆれで集計が3行に割れる（912–918行目）、循環参照で再帰CTEが返ってこない（1258–1265行目）、再計算で1,340円ずれる（1753行目）。いずれも「良くない」という評価ではなく、動かした結果の値が判決を下す形になっている。

**イベントソーシングの扱いが白眉。** やる夫に「これが真実の形だお！」（587行目）まで心酔させてから、3,000人の月給一覧（598–611行目）とペイロードのスキーマ進化（619–625行目）の二発で殺す。そしてやる夫自身が「死んだのは『状態を一切持たない』という原理主義の部分だお」（637行目）と魂と教義を切り分ける。この「棄却するか?」（631行目）への抵抗が、第7幕の両建て（1883–1895行目）へ正しく着地する。

**「保留」が明示的に積まれ、全部回収される。** 第1幕の状態か出来事か（169–171行目）、第3幕のずるい安上がりな手（827行目）、第4幕のIDが変わらないとは何か（1139行目）、第6幕の明細の氏名（1569行目）。4本の保留が第6幕・第7幕で全部解かれ、特に827行目の予告が1871行目で回収される呼応は気持ちがよい。

**制約の射程という一枚の表が全幕を貫く。** 2-2の武器庫の表（316–322行目）が、期間重複（731行目）、木の循環（1270行目）、最終まとめ（2073行目）で三度参照される。設計の議論に「どこまでDBに預けられるか」という座標軸を与えている。

**「そのときどうしてますか」の聞き込み技術。** 「ありえますか」では『いない』と返ってくるが、運用実態を聞くと備考欄の手動振込が出てくる（392–405行目）。「現場のExcel・備考欄・付箋は、モデルから漏れた多重度の死体置き場だ」（402行目）は本書で最も実務的に効く一文。

**参考文献19点、法令と規格を含む。** 労働基準法の条番号つき（2121行目）、SQL:2011、RFC 9562（2126・2134行目）まで押さえている。

## 欠点

**登場人物が2人しかおらず、やらない夫の攻撃が定型化している。** 「では反例をやる」「では攻撃する」「では判定してもらおう」が259・301・526・673・891・1024・1198・1255・1433・1631行目と10回以上ほぼ同じ形で繰り返される。カモメ製作所の総務・経理は連絡文（114–122行目、1349–1350行目）としてしか登場せず、一度も台詞を持たない。数値で反論する第三者がいないため、全ての判決をやらない夫が一人で言い渡す構造になっている。

**4-1のJSONB反例が事実として矛盾している。** 912–918行目の集計結果の表が出ているのに、直後に「`::numeric` のキャストが実行時エラーで落ちる」（921行目）と書かれている。エラーで落ちるなら表は出力されない。しかも表の「通勤 20000」は 12000+8000 で、122番の `"10,000"` が計算に入っていないことを示しており、表そのものが不整合。教材で最も鋭い反例の一つが、実行不能な出力を根拠にしている。

**やる夫が難所を一足飛びに越える場面がある。** 1463–1467行目で、人と雇用が別エンティティであることに反例3問だけで到達する。作者も「到達が速すぎる」（1470行目）と自覚して中間案（1472行目）へ巻き戻すが、この巻き戻しは教師の指示による人為的なもので、やる夫が自分で行き詰まった結果ではない。同様に427行目の「記録は1対多、ビューで1対1の顔」も、迷いの直後にほぼ最適解が一発で出ている。

**物語的な圧力がほぼない。** 買収（1150行目）は組織階層とスケールを持ち込む口実に留まり、納期も予算も存在しない。誰も怒らず、誰も困らず、やる夫が損もしない。実際に本番で壊れて金銭的被害が出るのは1,340円のズレ（1753行目）ただ一箇所で、それ以外の失敗は全て「INSERTする前にやらない夫が止める」形の机上演習になっている。苦労の過程とセットで学ぶという狙いに対して、代償の描写が弱い。

**性能の議論が定性的で数字がない。** UUIDv4の局所性の話（1661–1664行目）は「じわじわ効いてくる税」で終わり、行数もページ分割率も測定値も出てこない。3,000人・数十万イベント（603–605行目）も概算のみで、実際の実行時間が示されない。他の判断が全て実行結果で決着しているだけに、ここだけ印象論なのが目立つ。

**インデックス設計とNULLの照会挙動が抜けている。** 1042–1044行目でNULLの3つの意味に触れながら、`WHERE grade = 5` が NULL 行を落とすという三値論理の実害には一度も触れない。有効期間テーブルを大量に導入する設計なのに、`valid_from <= x AND x < valid_to` に対するインデックス戦略の話が最後までない。

**終盤に説教が集中する。** 2050–2076行目で三原則＋使い方6箇条が一気に列挙される。個々の内容は本文で獲得済みだが、最後の30行が箇条書きの羅列になり、それまで維持していた「反例で殴られる」テンポが失われている。

## 改善案

1. **4-1の反例を2段階に割る。** 912行目の表を出す前に、まず `SELECT DISTINCT key FROM employees, jsonb_each_text(allowances)` で「キーが4種類に割れている」ことだけを見せる。その次に SUM を含む集計を実行させて `invalid input syntax for type numeric: "10,000"` のエラーを出す。現状のように「表が出た上にエラーで落ちる」という両立不能な状態を解消でき、しかも「まず名寄せが壊れ、次に型が壊れる」と壊れ方が二重であることが明確になる。

2. **カモメ製作所の総務担当できる子を三人目のキャラクターとして立てる。** 特に2-3の聞き込み（388–399行目）は、現状やる夫が想像で自問自答しているだけで最も惜しい。ここを実際に総務さんに電話する場面にし、「いないですね」→やらない夫が質問を言い換えさせる→「あー、部長の鈴木さんだけ備考欄に…」と本人の口から出させる。この一人がいれば、第5幕の組織改編（1345行目）や第7幕の税務調査（1745行目）にも生身の圧力を持ち込める。

3. **納期と損害を物語に入れる。** 1150–1152行目の買収に「グループ統合のカットオーバーは来年4月1日、組織改編と同時」という期限を与え、第5幕の木×時間（5-3）が「間に合うか」の問題になるようにする。さらに第7幕の税務調査（1745行目）を第1幕の末尾で予告しておくと（例：やらない夫が「3年以内にお前は税務調査に立ち会う」と一言）、全幕が一本の締切に向かう。

4. **6-1の到達を一往復遅らせる。** 1463行目の一気の気づきの前に、やる夫が「退職フラグを戻す」案で粘る場面を挟む。そこで社会保険の資格取得届が前回の資格喪失日と矛盾して役所に突き返される、という実害を1件起こす。教師が「到達が速すぎる」（1470行目）と言って巻き戻す現状の作りは、教材が自分で構成を告白してしまっており不自然。

5. **UUIDの議論に実測を足す。** 1664行目の後に、100万行INSERTの所要時間とインデックスサイズを連番／v4／v7で並べた3行の表を置く。本書の他の判断が全て実行結果で決着しているので、ここだけ定性評価なのは浮いている。

6. **有効期間テーブルのインデックスを1節足す。** 3-4の排他制約（741–746行目）の直後に、`EXCLUDE USING gist` が作るGiSTインデックスがそのまま時点照会にも効くこと、`current_salaries` ビュー（691行目）が毎回全行走査になり得ることを、`EXPLAIN` の出力つきで10〜15行だけ見せる。第2幕の「制約の射程」に「性能」という軸が加わり、終盤の候補比較（1975–1993行目）にも根拠が増える。

7. **最終まとめを分散させる。** 2065–2076行目の使い方6箇条は、各幕の末尾（原則Iのまとめ436行目付近、原則IIの847行目付近など）に1〜2条ずつ配り、最後は第8幕の答え合わせ表（2020–2034行目）と三原則（2050–2063行目）だけで締める。終盤30行の箇条書きラッシュが解消される。
