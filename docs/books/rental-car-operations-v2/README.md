# やる夫が「一台しかない車」を五組へ貸すようです ── 連休前夜のレンタカー業務再設計

---
## 登場人物

**やる夫** ── 星空レンタカー駅前Bを営むフランチャイズ店主。

**やらない夫** ── 三店舗が整備と安全監査を委託する共同整備工場の経営者。

**できる子** ── 空港店の配車担当。三店舗の予約と車両配置を担当する。

**できる夫** ── 本部の機械学習エンジニア。店舗向けAIの開発を担当する。

**星野一家** ── 予約RES-501の顧客。大人2人、子ども3人で旅行を予定している。

> **共通トイ**：空港A・駅前B・郊外Cの三店舗、車両12台、予約24件、そして青いミニバンCAR-0427。

**やらない夫**：

**やる夫**：

**やらない夫**：

### 1-3　一列で一台を言い切れない ── 状態の直交分解

**やる夫**：
列を足したお！
現在地、貸渡中、返却済み、清掃済み、整備中、貸出可、鍵位置、契約状態、請求状態、次予約……横スクロールが隣の旅行代理店へ突入したお！

**やらない夫**：
壁を越えたからデータモデルが正しいとは限らない。
CAR-0427を今すぐ貸せない理由を、一つずつ別の質問にしろ。

**やる夫**：
どこにあるか。
誰がいつまで使う権利を持つか。
清掃と点検が済んだか。
安全上走れるか。
どの予約へ割り当てたか。
契約と料金が閉じたか、だお。

**やらない夫**：
その六つは、一緒に変わるか。

**やる夫**：
返却されれば利用権は戻るけど、清掃済みにはならない。
整備工場へ移しても契約料金は自動で確定しない。
予約へ割り当てても現物は移動しない。
……あっ、**車両には一つの状態があるんじゃなく、互いに別々に変わる状態軸がある**お！

**やらない夫**：
直交する状態（orthogonal states）として置いてみろ。

|状態軸|CAR-0427の現時点|次へ進める条件|
|---|---|---|
|所在|郊外C、C-R12|回送の完了記録|
|利用権|前契約の終了確認中|返却受付と契約終了|
|清掃|開始済み、完了未確認|清掃完了と忘れ物照合|
|車両安全|タイヤ警告で保留|点検合格または修理完了|
|予約割当|五予約へ重複候補|一予約へ確定、他は代替合意|
|料金|仮計算|燃料・距離・延長・通行料の確定|
|鍵|主鍵C、予備鍵B|車両所在と鍵の組合せ確認|

**やる夫**：
「返却済み」は利用権についての出来事で、「貸出可」は清掃、安全、鍵、所在、契約が条件を満たした結果だお。
同義語じゃなかったお。

**やらない夫**：
予備鍵Bを貸出可棚へ入れたら。

**やる夫**：
鍵だけ貸出可能を名乗る詐欺だお。
車両安全が保留、所在がCなら、鍵の状態が緑でも車両の貸出可は偽だお。

**やらない夫**：
では、画面に大きく一つだけ表示するなら何だ。

**やる夫**：
`貸出不可`と、未充足条件を並べるお。
`安全点検未完了 / 現在地C / 主鍵C / 予約競合5`だお。
色だけじゃなく理由を読めるようにするお。

**やらない夫**：
五組には、氏名を状態の鍵にするのか。

**やる夫**：
同姓同名、代表者変更、表記揺れで壊れるお。
車両はCAR-0427、予約はRES-501のような安定ID（stable identifier）で結ぶお。
星野さんの名前は表示属性で、約束を追う鍵は予約IDだお。

**やる夫**：
やる夫、列を増やす前に実体を分けられたお！
これでExcel国境紛争は終結だお！

**やらない夫**：
そんなわけねぇだろ、常考。

### 1-5　変更した約束を消さない ── 予約の版

08:35到着でも車を確保してもらえますか。

**やる夫**：
予約表の開始時刻を08:20から08:35へ上書きするお。

**やらない夫**：
太田さんは「08:35に必ず変更」と言ったか。

**やる夫**：
「遅れそう」「08:35到着でも確保できるか」と聞いたお。

**太田**：
早く搬出できれば08:20に着きます。
遅くとも08:35です。
そこから積込みに15分ほど見てください。

**やる夫**：
一つの開始セルへ押し込まず、来店窓08:20〜08:35、貸出完了期限08:50、さらに許容出発09:10と分けるお。

**やる夫**：

### 1-6　同じ返却が二度届く ── 重複と冪等性

**やる夫**：
夜間連携を再実行したら、CAR-0427の返却イベントが二行届いたお。
二回返却されたなら、利用権が二台分戻って在庫が増えるお！

**やらない夫**：
車は分裂しない。
二行のevent_idは。

**やる夫**：
どちらも外部ID`C-RET-7719`、発生19:42。
一行目は19:49記録、二行目は再送で07:30記録だお。

**やらない夫**：
記録時刻が違うから別の出来事か。

**やる夫**：
同じ出所ID、同じ車両、同じ発生時刻、同じ前後状態。
配送が二回で、業務上の返却は一回だお。
同じ入力を何度処理しても結果が一回と同じになる冪等性（idempotency）が要るお。

**やらない夫**：
二行目を削除するか。

**やる夫**：
受信した事実は消さないお。
`RECEIVED_DUPLICATE`として再送を残し、現在状態と料金イベントは一回だけ進める。
連携の不安定さも後で測れるお。

**やらない夫**：
では、event_idが別の`C-RET-7720`だが、同じ車両・同じ時刻なら重複か。

**やる夫**：
すぐ消せないお。
受付訂正、二人の共同確認、別契約の誤紐付けかもしれない。
出所の業務キー、前イベント参照、契約ID、内容を照合し、不明なら競合キューへ送るお。

**やらない夫**：
具体的な副作用を計算しろ。

**やる夫**：
返却時デポジット返金19,160円を、返却イベントごとに発行する設計なら二重で38,320円返す。
在庫カウンタも`+1`を二回なら、実車12台なのに13台と表示するお。

**やらない夫**：
状態を`貸出中 → 返却受付`と遷移させるなら、二回目は。

**やる夫**：
現在が返却受付だから前提不一致で止まる。
ただし「返却済みをもう一度返却済みにする」だけの実装では正常終了して副作用だけ二回出る。
状態値だけでなく、元イベントIDに副作用を結ぶお。

**やらない夫**：
APIがタイムアウトし、送信側が結果を知らず再送するのは珍しい魔法か。

**やる夫**：
普通に起こり得るお。
だから一回しか送られないことを祈らず、再送されても壊れない受け方を作るお。

**やらない夫**：
検算は。

**やる夫**：
同じ`C-RET-7719`を三回入力しても、利用権の遷移1回、料金確定1回、返金指示1回。
受信ログは3件、重複2件として残る。

### 3-3　始めるほど終わらない ── 仕掛かりとLittleの法則

**やる夫**：

**やらない夫**：

**やる夫**：
仕掛かり（work in process, WIP）を$L=12$台、完了率を$\lambda=4$台/時とするお。
Littleの法則（Little's Law）$L=\lambda W$から、[^ref-little]
$$W = \frac{L}{\lambda} = \frac{12}{4} = 3\text{時間}$$
平均3時間も滞留するお！

**やらない夫**：
一時間4台の完了率が変わらないまま、仕掛かりを20台へ増やせば。

**やる夫**：
$$W = \frac{20}{4} = 5\text{時間}$$
みんなを「作業中」にして安心しても、完了しない車を8台増やし、平均待ちを2時間伸ばすお。

**やらない夫**：
逆に仕掛かりを8台へ制限し、完了率4台/時を守れれば。

**やる夫**：
平均2時間。
新しい車を入れず、詰まりを解いて完了させるほうが速いお。

**やらない夫**：
この式だけで明朝の個別車両が2時間後に出ると保証できるか。

**やる夫**：
できないお。
Littleの法則は安定した長期平均の関係で、優先車、故障、開店直後の波、工程ごとの差を消してる。
個別の約束には時刻イベントと工程条件を使い、式は混雑の構造を見るお。

**やらない夫**：

**やる夫**：

**やる夫**：
「忙しいから全部始める」は、仕事を進めた実感を増やすお。
でも顧客が買うのは着手済み札じゃなく、貸出可の車だお。

**やらない夫**：

**やる夫**：

### 6-4　掛け算が小さい大事故 ── FMEA

**やる夫**：
未来の失敗を全部予言して、点数順に潰すお！
やる夫、明日から安全占い師だお！

**やらない夫**：
予言ではない。
工程ごとに、どう壊れるか、何が起きるか、なぜ起きるか、今どう検知するかを具体化しろ。

**やる夫**：
故障モード影響解析（Failure Mode and Effects Analysis, FMEA）だお。
重大性$S$、発生頻度$O$、検出困難度$D$を1〜5で仮評価し、積$RPN=S\times O\times D$を会話の入口にするお。

|故障モード|影響|S|O|D|RPN|現行防護|
|---|---|---:|---:|---:|---:|---|
|整備保留車を貸出可へ|安全上不適格な貸出|5|2|4|40|整備画面の警告|
|予約重複割当|店頭欠車・代替|3|4|3|36|担当者の目視|
|冬用装備未確認|雪路へ不適格車|5|2|3|30|赤い注意札|
|燃料イベント二重計上|誤請求|2|3|2|12|明細確認|
|返却写真の部位不足|損傷判定不能|2|4|4|撮影者の経験|

**やる夫**：
RPN順なら40、36、30、32、12……待て、写真不足は`2×4×4=32`だお。
表の並べ方も点数も、計算を手で確かめるお。

**やらない夫**：
RPN30の冬装備より、RPN36の予約重複を必ず先に直すか。

**やる夫**：
駄目だお。
重大性5の安全リスクは積が少し低くても先に扱う。
点数1〜5の刻み方で順位も変わるし、低頻度の重大事象を平均へ沈めないお。

**やらない夫**：
$S=5, O=1, D=1$ならRPN5だ。
燃料二重計上12より後回しにするのか。

**やる夫**：
しないお。
法令、安全、不可逆な顧客被害は別の優先条件へ置く。
RPNは真実の順位表じゃなく、見落とした故障モードと根拠の違いを議論する道具だお。

**やらない夫**：
頻度2の根拠は。

**やる夫**：
感覚で置かず、事件帳の件数と母数を見るお。
記録がないなら「不明」とし、仮点であることを示す。
検出困難度も、警告が出るだけでなく、必要な人が期限前に意味を理解できるかで測るお。

**やる夫**：
FMEAの成果は色付き表じゃないお。
上位の壊れ方へ対策、所有者、期限、残るリスク、再評価を結ぶことだお。

**やる夫**：
強い対策にも副作用があるお。

**やる夫**：

不適格なら配車候補から除外し、現物マーキングも照合する。
赤札は最後の補助で、主防護にしないお。

**やる夫**：
今後は札を貼る前に、「もっと強く、仕事の中へ埋め込めないか」を問うお。

**やらない夫**：
背中の96枚は剥がしてから言え。

### 6-6　止めた後にも仕事がある ── 縮退と回復

〜〜 20:30　気象更新 〜〜

**できる子**：

**やらない夫**：

**やる夫**：
なら通常どおり全部貸すお！

**やらない夫**：
二択から離れろ。

**やる夫**：
地域、時刻、目的、車両装備、運転条件、代替交通で層別するお。
安全な縮退運転（degraded operation）を設計するお。

|レベル|条件|業務|顧客対応|復帰条件|
|---|---|---|---|---|
|0 通常|警報なし、道路正常|通常貸出|通常案内|継続監視|
|1 制限|市街地積雪、冬装備適合|適合車のみ、余裕時間追加|経路・装備説明、変更可|道路と天候再確認|
|2 強制代替|目的地経路が閉鎖または装備不足|該当予約を停止|別経路、鉄道、延期、返金|経路開通＋再判定|
|3 全面停止|店舗周辺も危険、回送不能|貸出・回送停止|安全な待機と一斉連絡|責任者が証拠付き解除|

**やらない夫**：
停止を検知した後のカードを作れ。

**やる夫**：
`検知 → 停止 → 影響範囲の限定 → 顧客連絡 → 代替 → 復旧 → 事後学習`だお。
回復カード（recovery card）へ、発動条件、指揮者、連絡対象、使える代替、解除条件、記録先を入れるお。

**やらない夫**：
CAR-0427は冬用タイヤか。

**やる夫**：
台帳は「冬装備あり」だけ。
現物確認では四輪ともスタッドレスタイヤ、溝と空気圧合格、修理した右後輪も再確認済み。
ただし星野一家の目的地は北部山間路だから、道路閉鎖なら車が適格でも貸さないお。

**やらない夫**：
車両適格と旅程適格を分けたな。

**やる夫**：
RES-501へ21:00までに、通常案と道路閉鎖時の宿泊地変更・鉄道案・無償取消を説明するお。
安全停止は店の都合で黙って予約を消すことじゃないお。

**できる子**：
停止権限は誰が持つ？

**やる夫**：
現場は危険を見たら一時停止できる。
再開は同じ人の気分でなく、道路情報、装備、車両、安全責任者の条件で決める。
誤停止を責めず、長引く停止は指揮者が影響を限定するお。

**やらない夫**：
予防できない事象はある。

**やる夫**：
だから安全は「失敗ゼロ」の札じゃないお。
早く検知し、危険を通さず、影響を狭め、顧客を置き去りにせず、条件を確かめて戻す能力だお。

### 7-4　95%の残りに何がいる ── 損失分布

**できる夫**：
仮想評価200件で190件正解、精度95%です！

**やる夫**：
95点なら合格だお！

**やらない夫**：
間違えた10件を出せ。

**できる夫**：
安全・要確認の実例40件のうち、34件を拾い、6件を通常へ見逃しました。
通常160件のうち、4件を要確認へ過剰に回し、156件は正しく通常としました。

**やる夫**：
正解は`34 + 156 = 190`、確かに95%。
でも安全候補40件のうち6件を見逃してるお。

**やらない夫**：
二つの指標を計算しろ。

**やる夫**：
要確認と出した38件のうち本当に要確認は34件。
適合率（precision）は`34 ÷ 38 ≈ 89.5%`。
実際の要確認40件のうち拾えた34件だから、再現率（recall）は`34 ÷ 40 = 85%`だお。

**やらない夫**：
通常正解が多いと、全体精度が安全見逃しを隠す。

**やる夫**：
損失を仮置きするお。
見逃し一件の平均影響を50,000円相当、過剰確認一件の追加作業を1,000円相当とする仮想値なら、
$$6 \times 50,000 + 4 \times 1,000 = 304,000\text{円相当}$$
同じ10誤りでも内訳が逆なら全然違うお。

**できる夫**：
さらに6見逃しのうち1件はD3のタイヤ側面異常、5件はD1候補でした。
平均金額だけでも重大性の裾を消します。

**やらない夫**：
閾値を下げ、疑わしいものを全部人へ回せば。

**やる夫**：
再現率は上がるけど、選択率、つまり全件の何%を人へ送るかが上がる。
200件中150件を確認するなら、人の時間をほとんど減らせず、警告疲れでD3を見落とすお。

**できる夫**：
店舗別ではAの再現率90%、B88%、C65%。
Cの暗い屋上写真が弱いです。

**やる夫**：
全体95%で地区差も隠れてたお。
画像撮影環境を直す対策と、Cでは自動通過させない運用が必要だお。

**やらない夫**：
合格条件を言え。

**やる夫**：
全体精度だけでなく、D3見逃し0を評価集合で要求し、撮影品質不足は判定不能へ。
店舗別の再現率、選択率、人の処理時間、異議申立て、誤通過後の影響を見るお。

**やらない夫**：
評価集合で0でも、本番の0を保証はしない。

**やる夫**：
だから権限を限定し、監視と停止を置くお。
