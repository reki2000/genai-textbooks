# やる夫が「一台しかない車」を五組へ貸すようです ── 連休前夜のレンタカー業務再設計 の新アウトライン

## 再設計の方針

旧版の業務改善百科事典を解体し、青いミニバンCAR-0427の24時間へ全概念を収束させる。五組の顧客が同じ車を必要とする矛盾から始め、予約、現物、整備、清掃、契約、支払、拠点間移動の状態を一件ずつつなぐ。改善手法、データ、AI、CoEは独立章にせず、CAR-0427を連休初日の午前8時へ安全に渡すため必要になった順に出す。

## 第1幕　返却済みで、貸出中で、整備工場にいる

- CAR-0427が鍵棚では返却済み、予約画面では貸出中、整備画面では入庫中、現物は隣店にある。
- やる夫が一番新しい画面を正本と決め、時刻と更新元が違う反例で壊す。
- 現物状態、利用権、清掃・整備可否、所在、契約、料金を別の状態として分解する。
- 安定ID、イベント履歴、現在状態、出所、時刻を持つ一台の事件帳を作る。
- 五つの予約を顧客名でなく予約ID、時間窓、車格、代替条件、約束で固定する。

## 第2幕　予約は車を持つことではない

- 予約数と車両数が同じなら必ず貸せる案を、返却遅延、整備、乗り捨て、充電、車格条件で壊す。
- 在庫を物理台数でなく、場所×時間×適格状態の容量として再定義する。
- no-showとキャンセルを見て過剰予約する案を、分布の裾で五組同時来店する反例へ通す。
- overbooking、バッファ、代替車、アップグレード、他社調達を、期待利益と最悪損失で比較する。
- 需要予測を点ではなく区間で持ち、祭り、天気、便到着、地域イベントを更新要因にする。

## 第3幕　返却から次の鍵までのピットレーン

- 返却処理5分だけを短縮し、清掃待ち・給油・点検・整備で2時間遅れる。
- 到着、受付、忘れ物、燃料・充電、洗車、清掃、損傷確認、整備判定、貸出可の流れを一枚につなぐ。
- タッチタイム、待ち時間、手戻り、仕掛かりを色分けし、Littleの法則で混雑を読む。
- 洗車機ではなく点検ベイがボトルネックだと発見し、全員を速くする案から制約を守る案へ変える。
- 標準作業を平均車だけで作り、ペット毛、雪、忘れ物、事故、EV低充電で崩れる。例外レーンと復帰条件を作る。
- CAR-0427の鍵が物理工程より先に「貸出可」棚へ移る小事故を、状態遷移の禁止条件で止める。

## 第4幕　三店舗で一台を奪い合う

- 空港店、駅前店、郊外店の12台と24予約を、三時間刻みのボードへ置く。
- 全店の余剰合計は正でも、必要地点・時刻に車がなく欠車することを数える。
- 乗り捨て、回送、顧客誘導、価格差、公共交通連携を、移動費と顧客負担で比較する。
- 最短距離で回送する案を、運転手の帰路、営業時間、充電器、道路混雑で壊す。
- ネットワークフローの小さな表を手で解き、CAR-0427を動かすと別予約が欠ける連鎖を見る。
- 地域別最適をやめ、全行程の所有者と判断期限を決める。

## 第5幕　傷はいつ、誰のものになったか

- 返却時の擦り傷を写真一枚で請求し、撮影時刻、角度、既存傷、利用規約が欠けて異議申立てを受ける。
- 出発前・返却後の証拠、顧客確認、損傷分類、修理見積、免責、休車損害を一連の判定へする。
- 燃料、走行距離、延長、通行料、清掃費、デポジットを、料金イベントとして上書きせず残す。
- 公平性と不正対策を二項対立にせず、説明可能性、異議申立て、証拠保存、個人情報最小化を設計する。
- 「顧客を信じる／疑う」から、双方が後で同じ履歴を再現できる契約へ移る。

## 第6幕　注意書き97枚の店

- 過去事故ごとに貼った注意書きが97枚になり、重要なタイヤ警告が埋もれる。
- slip、mistake、violationを、CAR-0427の鍵移動、車格選択、近道運用で区別する。
- スイスチーズモデルとFMEAを、重大性、発生、検出だけの掛け算を盲信せず優先順位の対話に使う。
- 注意、チェックリスト、独立照合、システム制約、物理ポカヨケを、強さと副作用で比較する。
- 予防だけでなく検知、停止、縮退、復旧、顧客連絡、再発学習を一枚の回復カードへする。
- 大雪で全車を止める／通常運転するの二択を壊し、地域、装備、目的、代替ごとの安全な縮退を設計する。

## 第7幕　AI店長は鍵を持てるか

- 予約、メール、傷写真をAIへ全部渡して自動判定させる案を、個人情報、幻覚、境界例、モデル変更で壊す。
- 需要予測、メール分類、画像候補提示、料金計算、貸出可判定を、確率的支援と決定的規則へ分解する。
- 代表例、境界例、過去失敗、地区差を含む評価集合をCAR-0427の事件から作る。
- 精度95%を、残り5%の損失分布、選択率、見逃し、異議申立てで読み直す。
- human-in-the-loopを、見る理由、時間、証拠、停止権限、追認率まで設計する。
- 影運用、段階展開、ロールバック、モデル・プロンプト・データ版管理で変更を業務として扱う。

## 第8幕　改善室が新しい渋滞になる

- 全改善を本部専門家へ集め、承認待ちで現場が止まる。
- 中央は標準、部品、教育、ガードレール、横断測定を持ち、店舗は観察と小さな改善を持つハブ・スポークへする。
- process、data、technology、vehicle safetyの所有者を分け、境界の共同判断を定例化する。
- KPIを処理件数だけにせず、欠車、初回完了、待ち時間、再作業、安全停止、回復時間、顧客結果へつなぐ。
- 日次の異常処理、週次の改善、月次の構造変更を運営リズムにし、暫定対応へ期限と所有者を付ける。
- CAR-0427の事件帳を教材化し、個人の武勇伝ではなく再利用可能な判断パターンにする。

## 終幕　午前8時、五組の鍵

- 五組が実際に来店し、CAR-0427一台を奪い合うのではなく、代替条件、時間窓、三店舗の車、公共交通を組み合わせる。
- やる夫は安全上の失格条件を先に守り、車格アップ、時刻変更、他店回送、返金を顧客ごとに説明する。
- CAR-0427は予定どおり一組へ渡るが、成功の証拠は鍵でなく全五予約が合意した結果へ到達した履歴にある。
- 夕方、新しい車両IDの鍵が「現在地：屋上」と表示され、やる夫が事件帳を開いて閉じる。

## 依存と検算

- CAR-0427、三店舗、12台、24予約、五組の予約IDを第1・4幕で固定する。
- 状態分解とイベント履歴は全幕の共通言語。第5幕の料金・損傷、第7幕のAI入力、第8幕のKPIへ流用する。
- 鍵が状態より先に動くギャグは第1・3・終幕で意味を変えて反復する。
- 97枚の注意は第3幕まで背景に増え、第6幕で主事件になる。
- AIは第1〜6幕で定義した対象だけを支援し、曖昧な現行業務を魔法で解かない。
- 終幕は全員へ同じ車を用意することを成功条件にせず、顧客成果と安全な代替を検算する。
