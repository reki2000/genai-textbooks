# 教材へ説明図を追加する

図を本文の飾りではなく、読者が文章だけでは保持しにくい関係・状態変化・比較を外在化する道具として作る。本文の説明と同じ情報を箱へ詰め直すだけの図は置かない。

## 1. 図にする箇所を選ぶ

対象教材の問い、幕・節見出し、前後の会話を読む。候補ごとに、図が答える「一つの視覚的な問い」を書く。

- 幕や節の全体像を一望する必要があるなら、関係図・階層図・比較図にする。
- 値やインスタンスが処理ごとに変わるなら、同じ対象を段階間で追える状態遷移図にする。
- 添字、範囲、対応関係の取り違えが起きやすいなら、具体例へ位置番号と強調範囲を付ける。
- やる夫式教材では、素朴案が具体的反例で壊れる瞬間と、修正後に同じ例が通る形を優先する。可能なら一枚へ前後を並置する。
- 桁違いの数量、幾何・空間、複数段のパイプラインは、文章より視覚化が効く候補として優先する。
- 三つ以上の要素、段階、分岐がなく、短い文や式で同等に伝わるなら図にしない。

教材全体を均等に図入りにしようとしない。認知負荷が高く、後の推論の足場になる箇所を優先する。一枚には一つの主張だけを持たせ、原則として一節に一枚までとする。多数の図を追加する場合は、着手前に「位置・視覚的な問い・読み取れる結論」の候補一覧を示す。枚数そのものを目標にしない。

## 2. 本文との役割を設計する

図を置く直前までに、読者が入力・記号・目的を知っている状態にする。導出や具体例の直後、会話がその意味を解釈する直前へ置くのを基本とする。

図には次を含める。

- 本文と同一の値、記号、添字規約
- 視線の開始点と、読む順序が分かる配置
- 変化しない部分と、現在注目する部分の視覚的な区別
- 図だけを見ても何を示すか分かるタイトルまたは短い結論

本文には相対パスのMarkdown画像と、一文のキャプションを置く。代替テキストは「概念図」ではなく、図が示す結論を具体的に書く。図の全内容を本文から図へ追放しない。細部を持つ図は画像自身へのリンクで包み、狭い画面からタップして原寸表示できるようにする。

```markdown
[![二段階の標本と短い残りを足してrankを求める図](figs/rank-two-level.svg)](figs/rank-two-level.svg)

図2-1：`rank_1(14)=3+2+1=6`。大区画、小区画、残りの実測を足す（タップ／クリックで原寸表示）。
```

## 3. 表現方法を選ぶ

次の順で、学習上の仕事を最も正確に果たす媒体を選ぶ。

1. 箱、線、座標、記号、具体値で表せる構造・アルゴリズム・量的比較は、コード生成SVGにする。
2. 建造物、装置、史料など、実在物そのものを見ることに意味がある場合は、権利と利用条件を確認した外部画像を引用してよい。
3. 生物、流体、自然現象、数学的対象など、幾何学的な作図では本質を損ない、適切な外部画像もない場合は、`imagegen` スキルでオリジナルのラスター画像を生成してよい。

### 外部画像を引用する

画像ファイルをダウンロード、複製、加工してリポジトリへ置かない。原掲載ページを確認し、公式提供、パブリックドメイン、オープンライセンス、または引用として必要性と主従関係を説明できるものだけを使う。サイトの利用規約が外部埋め込みを禁じる場合、期限付きURLしかない場合、権利者や原典を特定できない場合は使わず、別の資料かオリジナル生成へ切り替える。

外部画像は原掲載ページへのリンクを張り、直下へ作者・提供者、作品または資料名、原掲載ページ、ライセンスまたは引用目的を記す。単なる雰囲気づけは引用の必要性にならない。外部画像URLは `docs/books/<id>/figs/` へコピーせず、教材別Pythonスクリプトの生成対象にも含めない。

```markdown
[![画像が学習上示す内容](https://example.org/path/image.jpg)](https://example.org/original-page)

*出典：作者・提供者「資料名」[原掲載ページ](https://example.org/original-page)。CC BY 4.0／本文の装置構造を比較するため引用。*
```

### オリジナル画像を生成する

`imagegen` スキルの手順に従い、用途を `scientific-educational` として、必要な対象、視点、ラベル、正確性制約、避ける表現をプロンプトへ固定する。生成画像内へ長い説明文や数式を焼き込まず、正確なラベルは本文または後段のコード処理で補う。出力は `docs/books/<id>/figs/` へ保存し、教材別Pythonスクリプト側で存在確認、寸法、ファイル名などを検証対象に含める。生成に用いた最終プロンプトと生成手段は、教材別の同じPythonスクリプト内へコメントまたは定数として残す。

生成後は、見た目の自然さではなく、本文と形態・因果・スケール・ラベルが矛盾しないかを検査する。科学的に重要な細部をモデルが創作した疑いがあれば採用しない。

## 4. 再現可能な生成コードを作る

教材IDを `<id>` として、生成元と生成先を固定する。

```text
scripts/figs/<id>.py              # その教材の全図を生成する唯一のコード
docs/books/<id>/figs/<name>.svg   # 本文が参照する生成物
```

同じ教材の図を別のPythonファイルへ分散させない。複数教材で再利用する描画部品だけ `scripts/figs/` 配下の共通モジュールへ切り出してよい。生成物を手で編集しない。

追加依存を安易に増やさず、線・箱・文字・矢印が中心ならPython標準ライブラリでSVGを生成する。既存の描画依存がある場合はそれに従う。スクリプトはリポジトリ直下以外から呼ばれても出力先を解決し、出力順・数値表記・メタデータを決定的にする。`--check` で既存図と再生成結果を比較できるようにする。

既存の共通描画モジュールと配色を先に確認し、適合するなら再利用する。新しい共通部品は `scripts/figs/` 配下へ置く。座標、曲線、尺度、数値は本文の式や入力値から計算し、目分量で結果らしい形を作らない。

各SVGへ `<title>` と `<desc>` を入れ、狭い画面でも読める `viewBox` を設定する。原則として `width` / `height` 属性は付けず、縦横比を保って本文幅へ収める。ダークテーマでも読める明るいカード面をSVG内に持たせる。

色だけに意味を持たせず、ラベル、線種、枠のいずれかを併用する。系列は一枚3色程度までとし、凡例より対象への直接ラベルを優先する。赤は失敗・危険・棄却を示す強調へ予約する。日本語の字形を含むフォントフォールバックを指定する。KaTeXはSVG内で動かないため、長い数式は本文へ残し、図には計算結果と必要最小限の記号だけを置く。

生成SVGも本文と同じソース成果物として扱い、生成コードとともにコミット対象にする。生成物を直接修正しない。

## 5. 自己検証する

図ごとに本文の具体例を最初から再計算し、すべての値、範囲端、矢印、ノード対応を照合する。その後、次を実行する。

```bash
python3 scripts/figs/<id>.py
python3 scripts/figs/<id>.py --check
python3 scripts/yaruo_lint.py docs/books/<id>/README.md --check --verbose
python3 scripts/generate_site.py
git diff --check
```

`generate_site.py` が不足パッケージだけを理由に停止し、`uv` と `requirements-dev.txt` が利用できる場合は、グローバル環境へインストールせず次で検証する。

```bash
uv run --with-requirements requirements-dev.txt python scripts/generate_site.py
```

生成した図を実際に開き、デスクトップ幅と約360px幅で、文字の重なり、切れ、読む順序、強調の識別を確認する。360pxではタイトル、主経路、結論が分かることを必須とし、細部を読むための原寸リンクと、図を開かなくても結論が残るキャプションを付ける。すべての細字を縮小状態で読ませようとして情報を削らない。ビルド結果でも画像パスと原寸リンクを確認する。

行数や文字幅を目算だけで判定しない。全SVGをPNG化し、一枚ずつ実画像で確認する。`@resvg/resvg-js` が利用できる場合は次を使う。

```bash
mkdir -p /tmp/svgshot && cd /tmp/svgshot && npm install @resvg/resvg-js
cd - >/dev/null
node .claude/skills/textbook-figures/scripts/render_svg.js docs/books/<id>/figs /tmp/svgshot/out
SVG_RENDER_WIDTH=360 node .claude/skills/textbook-figures/scripts/render_svg.js docs/books/<id>/figs /tmp/svgshot/out-360
```

日本語フォントがない環境では、利用可能な日本語フォントをラスタライザへ読み込ませてから判定する。システムへ導入しない一時フォントは `SVG_FONT_FILES=/path/to/font.ttf`（複数はOSのパス区切り文字で連結）として上のコマンドへ渡せる。修正したら再生成・再描画し、重なり、はみ出し、無駄な空白、矢印や極値の位置を再確認する。

外部画像がある場合は原掲載ページの到達性、表示可否、出典表記、利用条件も確認する。生成画像がある場合は最終プロンプトと採用画像の対応を確認する。

## 6. 図版レビューを行う

本文の通常レビューとは別に、追加した各図を次の観点で受け入れ検査する。

| 観点 | 合格条件 |
|---|---|
| 正確性 | 本文と値・添字・用語が一致し、図だけから誤った対応を読めない |
| 説明上の仕事 | 図が関係、変化、比較の少なくとも一つを文章より追いやすくする |
| 配置 | 入力を導入した後、図を使う解釈や次の推論より前にある |
| 可読性 | 360pxでもタイトル・主経路・結論が分かり、細部へ原寸リンクで到達でき、色覚に依存しない |
| 非重複性 | 本文や別図の単なる言い換えでなく、一枚一主張になっている |
| 保守性 | Pythonが唯一の生成元で、`--check` とビルドが通る |
| 権利・由来 | 外部画像は複製せず原典・条件・引用目的があり、生成画像は生成手段とプロンプトを追跡できる |

指摘には図名、本文位置、観察事実、学習への影響、具体的な修正案を書く。レビューで値の誤り、主経路の曖昧さ、本文との矛盾が見つかったら生成コードを直し、全図を再生成して再検査する。

完了時は、追加した図の一覧、挿入位置、生成コマンド、検証結果に加え、検討したが図にしなかった候補と理由も報告する。
