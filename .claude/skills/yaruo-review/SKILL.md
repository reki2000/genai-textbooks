# やる夫式教材 受け入れレビュー

外部（別モデル・別セッション・人間）が執筆し、この形式の教材として成立しているか未検証の `docs/books/<id>/README.md` を検査する工程。

**このスキルは執筆基準を再定義しない。** 境界は3層。

| 層 | 正本 |
|---|---|
| 作品に要求する性質 | `yaruo-rediscovery/SKILL.md` と `references/section-card.md`・`anti-patterns.md` |
| 数値制約（字数帯・往復・発言長） | `scripts/yaruo_lint.py` の定数 |
| **証拠の取り方・指摘票・影響度と処置・権限・二者照合・報告形式** | **本スキル** |

書式崩れは `yaruo-format`、事実・出典・数式の検証は `yaruo-proofread`、書き直しの作法は `yaruo-rediscovery`。**ここからそれらを実行しない。** 該当する問題は指摘票に載せ、送り先スキル名を書くだけでよい。

## 権限（先に確定させる）

| ユーザーの指示 | できること |
|---|---|
| 「レビューして」「品質をみて」 | **読み取りのみ。本文を編集しない。** 指摘票と報告で止める |
| 「レビューして直して」「修正して」 | 指摘票を作った後、処置区分に従って編集する |
| 「codexと」「二人で」「両者で」 | 二者レビュー（下記）。単独か二者かは修正権限とは独立 |

**既定は読み取りのみ。** 影響度が critical でも、修正指示がなければ直さない。

## 手順

### Step 0: 機械検査を先に通す

人手を使う前に、機械で分かるものを落とす。

```bash
python3 scripts/yaruo_lint.py docs/books/<id>/README.md --check --verbose
```

- **error** は欠陥として指摘票へ転記する（`yaruo-format` / 執筆側の担当）。
- **warning / info は品質の判定に使わない。** 幕ごとの発言長分布・実効往復・高速区間は、Step 2 で**どこを重点的に読むか**を決める材料としてだけ使う。

続けて、同型反復の候補区間を機械で出す。

```bash
python3 scripts/yaruo_beat_repetition.py docs/books/<id>/README.md --show
```

出るのは `same-beat-run` の候補区間と、その会話の具体。**候補であって合否ではない。**
Step 2 の観点1でどこを重点的に読むかを決める材料にする。**0件でも通読を省略しない**
（表層の統計が動いていて型だけ同じ区間は、この層では落ちる）。判定の正本は
`references/beat-labels.md`。

### Step 1: 骨格と問いを固定する

`grep -n '^#\{2,3\} ' <教材.md>` で幕・節を一覧し、`catalog.yml` の `question` と `plot` を読む。**教材が答えると宣言した問い**を1行にメモする。以降の全指摘は、この問いへ近づけるかで重み付けする。

### Step 2: 3観点を同時に当てる

幕順に通読し、3観点を**同時に**当てる（観点ごとに3周しない）。読み終えたら**全体横断表**を作る。設定の因果・伏線・感情曲線・ツアー比率は、全文を把握しないと判定できない。

| 横断表 | 記録する列 |
|---|---|
| 6段表 | 核心概念 × 課題／素朴案／具体的反例／原因の言語化／修正／検算。各セルに行番号。**空セルが欠落の証拠** |
| 設定要素表 | 舞台・小道具・立場ごとに 導入位置／後の使用位置／担う仕事（課題・反例・検算・感情・伏線） |
| 伏線表 | 設置位置／回収位置／未回収なら空欄 |

#### 測定の作法（省くと、撤回される指摘になる）

話者行から機械的に確定する量は `--stats` が出す。**その場限りの集計スクリプトを自分で書かない。** 二者レビューで双方が同じ数字を見るための共通の土台でもある。

```bash
python3 scripts/yaruo_lint.py docs/books/<id>/README.md --stats
```

出るのは幕別の話者バランス（発言数・字数・平均・字数比）と、見出し末の話者（母数つき）。**合否には使わない診断値**で、Step 2 のどこを重点的に読むかを決める材料にする。

語の一致で数えるもの（承認語、素朴案、命名の位置）は `--stats` に無い。自分で探すことになるので、次を守る。

1. **機械一致は候補であって測定ではない。** 件数を指摘にするなら、全ヒットを目視し、採用と誤検出へ分けた表を出す。grep のヒット数をそのまま件数として書かない。
2. **出力が空の集計は「該当なし」ではなく「未実施」。** 集計が0件を返したら、まず集計側を疑う。空の結果を根拠に、問題ありとも問題なしとも書かない。
3. **分子だけの主張を書かない。** 「N節中M節」は、N の求め方を書けるときだけ使う。母数を確定できない量は指摘票に載せない。節の母数は見出しレベルで変わるので、`###` と `####` のどちらで数えたかを明記する。
4. **教材が自分で使う数詞・固有名は全件 grep する。** 題名・幕見出し・結論の数詞、索引と本文の対応、伏線の語。既に気づいた語だけを引くと、題名と結論の矛盾を見落とす。

#### 観点1: エンタメ性（ドラマ・コメディ・設定・単調さ）

正本は `anti-patterns.md`（処方箋）と `section-card.md`（必ず入れる3つ／やってはいけない3つ）。ここでは**何を証拠として記録するか**だけを定める。

- **場面**：幕冒頭に時間・場所・利害のある出来事があるか。宣言型の導入（「今日は〜を学ぶ」）の行番号。
- **設定**：設定要素表の「担う仕事」列が空の要素。判定は**設定の豪華さではなく、学習上またはドラマ上の因果を担うか**。後の幕での再利用は強い証拠だが必須条件ではない（抽象的なテーマでは簡素な舞台が妥当）。
- **登場人物欄**：複数の幕にまたがって登場するのに欄に無い話者の名前（単一の幕・節だけの話者は欄に無くてよい）。1人100字を超える項目。作中の行動描写（「答えを教えず、反例と問いで導く」など）と、正体・結末・人物の到達点を予告するネタバレの行番号。正本は `yaruo-rediscovery` の「冒頭の『## 登場人物』欄」。
- **感情**：幕ごとの感情の型を並べ、隣接幕で同型が反復している箇所の節見出し。
- **笑い**：ボケ・ツッコミの位置と、それが素朴案の伏線・反例の条件・後の幕の回収のどれと結び付くか。結び付かないものの行番号。禁止域（重傷・重病・死・生活破綻・深刻な侮辱）は行番号つきで即報告。
- **単調さ**（このスキルの主戦場）：
  - Step 0 の候補区間と、**対照として同じ教材の非候補区間**にビートラベルを付ける。
    ラベル集合・指標・実行方法は `references/beat-labels.md` が正本。
    語の一致で「同型」を主張しない。**同型反復は語の一致ではなく関係の型の一致**であり、
    語彙が毎節入れ替わりながら型だけ残る例が実在する。
  - 「教師が問う → 生徒が答える」の同型が4連続以上続く区間の行範囲。
  - 節末の閉じ方の型を全節ぶん並べ、同型が連続する箇所。最後の発言者が固定されていないか。
  - 承認語が転換点以外に置かれている行番号。
  - **削除しても推論と感情が変わらない発言**の行番号。これが水増しの唯一の判定基準。

#### 観点2: 学習内容の深さと正しさ

- **深さ**：Step 1 の問いに結論が実際に答えているか。用語の言い換えで終わっていないか。「なぜ」まで降りずに「そういうものだ」で止まった箇所の行番号。
- **知識予算**：やる夫が、前提知識＋作中で到達済みの内容を超えた知識を披露している行番号。概念が定義前に使われている箇所（定義位置と使用位置の2点を記録）。
- **藁人形**：素朴案が初学者の本当に思いつく案か。誰も採らない案を潰して勝ったことにしている節。
- **正しさ**：明らかな事実・数値・式の誤りだけを記録し、検証は `yaruo-proofread` へ送る。
- **ツアー化**：歴史・分派・応用を巡るだけの部分の行数を実測し、全体に対する比率を出す（正本の上限は20%）。

**やる夫の素朴案・誤答を「誤り」として指摘しない。** 直後に反例で潰されていれば意図された誤りであり、物語装置である。

#### 観点3: 再発見の過程（苦労とセットか）

6段表の空セルがそのまま指摘になる。特に多い欠落：

- **反例をやる夫が手を動かして確認していない**（教師が破綻を宣告して終わる）。
- **原因の言語化を教師が代弁している**（やる夫が自分の言葉で失敗の構造を述べていない）。
- **検算が無い**（新しい道具を具体例へ適用して動くことを確認していない）。
- **教師が指示し、やる夫が一発で正解する**（`instruction-and-plain-answer`）。**最も避けたい型。**
  やる夫の回答に素朴な誤答も逡巡も無く、教師の発言が問いかけでなく命令に寄る。
  再発見ではなく知識の羅列に落ちている。ビートラベルの**苦労率が0の区間が3単位以上続いたら
  ここへ挙げる**。単調さ（観点1）ではなく**この観点の指摘**として書く。
  区間が1単位でも成立するので、同型反復の候補に載らなくても見る。

加えて、命名がやる夫の到達より先に来ていないか、失敗が後の幕で足場として再利用されているか、伏線表に未回収が残っていないか。

### Step 3: 指摘票を作る

指摘は**1件1行の表**にする。列は固定。

| 列 | 内容 |
|---|---|
| ID | `E1` `E2`…（観点1）／`L1`…（観点2）／`R1`…（観点3） |
| 観点 | 1／2／3 |
| 証拠位置 | 局所なら**行番号＋最小限の引用**。不在・反復・構造の問題なら**節見出しと行範囲／比較する2箇所以上の行番号／6段表の欠落セル** |
| 観察事実 | 見えたものだけ。「退屈」「浅い」のような感想語だけの指摘は書かない |
| 基準への影響 | どの正本のどの規定に触れるか |
| 影響度 | critical（教材として成立していない）／major（質を明確に落とす）／minor（好みの範囲） |
| 処置 | 報告のみ／局所修正可／構成変更につき要承認 |
| 提案 | 具体的な直し方 |

**影響度と処置は独立の2軸。** 重大な問題ほど局所修正できるとは限らない（再発見サイクルの欠落は critical だが、たいてい構成変更を要する）。

**証拠位置を書けない指摘は票に載せない。**

**行番号は本文が変わった瞬間に無効になる。** 修正後に票を読み直すとき、行番号を信じて再確認しない。`--stats` と grep で位置を取り直してから照合する。修正を伴う協議では、結論文書に行番号だけを残さず、引用の断片も併記する。

### Step 4: 処置する（修正権限がある場合のみ）

- **局所修正可**：台詞の追加・分割・入れ替えで直る範囲。実行する前に `section-card.md` を読み直す。
- **構成変更につき要承認**：幕の入れ替え、節の新設・削除、大幅な加筆。**断行せずユーザーへ提案する。**
- **報告のみ**：何もしない。

修正では**語尾・一人称・キャラクター、そして意図された誤りを壊さない**。

### Step 5: 報告する

- 観点ごとの指摘数と、影響度 critical/major/minor の内訳
- 処置区分ごとの一覧（IDと証拠位置つき）
- 修正した場合は**修正前→修正後**の一覧
- 他スキルへ送る項目（書式 → `yaruo-format`、事実・数式 → `yaruo-proofread`）
- 3観点それぞれについて、指摘0件なら「見た上で問題なし」と明示する

## 二者レビュー（Codex ⇄ Claude）

狙いは、**両者が独立に同じ節・同じ欠陥種別を挙げたか**で証拠の強さを測ること。担当を観点で分割すると、この一致が測れなくなるので**分割しない**。

プロトコル（`discussion/CURRENT`、通番、相手宛以外を書かない）は `discuss` スキルに従う。ここで上書きするのは順序だけ。

1. **招待便（指摘非開示）**：開始側は `1.to-<相手>.md` に**対象パス・Step 1 の問い・モード・修正権限の有無だけ**を書く。**指摘内容を書かない。** 書くと受信側が独立レビュー前に読んでしまう。
2. 開始側は自分のレビューを手元で完成させ、指摘票を固定する。
3. 受信側が独立にレビューを完成させ、指摘票を返信する。
4. 開始側が初めて自分の固定済みリストを提示し、**同時に相手の各IDへ 同意／不同意／影響度の修正 を明示する**。「おおむね同意」で流さない。不同意には、意図された誤りである・伏線である・後の幕で回収されている、といった**本文の根拠**を付ける。
5. 照合キーは引用文の一致ではなく **`観点 + 対象節 + 欠陥種別`**。重複は証拠を強めるが、**多数決で影響度を自動決定しない。** 不一致は消さず、根拠とともに残す。

修正権限がある場合：

6. 適用する指摘IDと修正方針の確定案を番号付き交換ファイルへ書き、相手が各IDへ同意して **実装前合意** と明記する。
7. `CURRENT` を維持したまま、**議論開始側だけ**が本文を編集する（同一ファイルの同時編集を避ける）。
8. 相手が差分を確定リストと照合する。範囲外の変更や未達があれば番号付きファイルで差し戻す。
9. 双方が最終合意した時点で `conclusion.md` を書き、`discuss` の status 手順で双方の検証済みを確認してから `CURRENT` を削除する。

割れたまま残った項目は折衷せず、「両者で判断が割れた点」としてユーザーへ報告する。
