# やる夫式教材 校正・検証スキル

対象は `yaruo-rediscovery` が生成した会話形式の教材。処理は4つで、順番は必ず **1→2→2.5→3**。

**前提**

- 書式整形（カギカッコ・強調記号・表・句点）は `yaruo-format` の担当。ここからは実行せず、崩れに気づいても報告に載せるだけでよい。
- 参考文献の**書式規約**は `.claude/skills/yaruo-rediscovery/references/citation.md` が正本。脚注を付与・格上げするときはそれに従う（規約をここへ複製しない）。
- 正確な文字数や読了時間が必要なら `yaruo-count` を使う。概算はファイルサイズ÷3。

ファイルが大きいので一度に全部読まない。最初に `grep -n '^## '` で幕構成を把握し、以降は幕単位で読み書きする。作業メモ（主張リスト・脚注の通し番号・修正記録）はスクラッチパッドに置き、幕をまたいで維持する。

## 最重要の原則：意図された誤りを訂正しない

この教材形式は「生徒がわざと間違える」構造（素朴案→反例→修正の再発見サイクル）を持つ。**やる夫の素朴案や誤答は物語装置であり、訂正してはならない。** 直後にやらない夫が反例で潰していれば、それは意図された誤りである。

訂正対象は「教材が正しいと提示している記述」——主にやらない夫の解説と、最終的に到達した結論——に限る。すべての処理に適用される。

## 処理1: ファクトチェックと参考文献

### 対象の選別

**事実・理論・歴史について検証可能な主張をしている発言**：固有名詞（人物・研究・機関）、年号、統計値・実験値、定理や発見の帰属、歴史的経緯。キャラクターの感想・比喩・純粋な論理展開・数式変形（処理3の担当）は対象外。

### 手順

1. **全幕を通して読み**、検証可能な主張を作業メモに一括で列挙する（発言者・行番号・主張の要約）。Web検証は幕ごとに分けず、主張を出し切ってからまとめて処理する。
2. 主張を**想定ソースごとにグルーピング**する。1ページが複数主張をカバーすることが多い。同一ソースは同じ脚注番号を再利用するので、この時点で番号を割り当てる。
3. **Web検証はインラインで行うが、ページ本文をコンテキストに持ち込まない。** ソースグループごとに次の段構えで検証し、結果（判定・訂正/改善案・URL・正式タイトル・サイト名）を作業メモに主張と対応づけて保存する。
   - **第1段：Wikipedia summary API（トークンほぼゼロ）。** `curl -s "https://en.wikipedia.org/api/rest_v1/page/summary/<記事名>" | jq '{title, extract, url: .content_urls.desktop.page}'`（日本語版は `ja.wikipedia.org`）。要旨で裏が取れる主張はここで完了し、脚注に必要な URL・タイトルも揃う。
   - **第2段：WebFetch**（要旨で足りない主張・Wikipedia 以外）。WebFetch は本文でなく `prompt` への回答だけを返す。1ソース1回、prompt に主張リストと出力形式を明記する：「以下の各主張について (a) 判定（本文が裏付ける／矛盾する／記載なし）、(b) 主張をより正確にする訂正・改善案（不要なら『改善案なし』）、(c) ページの正式タイトル、を簡潔に返せ」。長文引用を求めない。
   - **第3段（任意・一次資料）**：発見や定理の帰属、教材の結論に関わる重要な主張だけ。WebFetch 2回で、(1) Wikipedia 記事へ「この主張を裏付ける一次資料の著者・題名・URL を返せ。本文引用は不要」、(2) 得た URL へ「本文が裏付けるか（裏付ける/矛盾する/記載なし）と正式タイトルだけ返せ」。裏付けが取れたら**脚注を一次資料へ差し替える**。周辺の定番事実は summary 止まりでよい。
   - **フォールバック禁止（コストの裾を固定する鉄則）**：第3段が失敗（403・リダイレクト・「記載なし」）したら WebSearch へ落とさず、その一次資料は諦めて Wikipedia を出典のまま残す。これで「成功時＝極小トークン、失敗時＝Wikipedia 止まり」に上限が固定される。
   - 互いに独立した curl / WebFetch は1メッセージにまとめて並列発行する。citするページが分からない、または主張が本当に怪しいときだけ WebSearch を使う（最後の手段）。`en.wikipedia.org` はほぼ確実に開けるが、公式サイトは 403 で空振りしやすい。
   - **記載する URL は curl か WebFetch で実在確認したものに限る。開いていない URL を書いてはならない（捏造は最悪の失敗）。**
4. 「記載なし」だった主張のうち、教材の結論に関わる重要なものだけ追加調査する。それ以外は保留。
5. 判定に応じて処置する。**どの判定でも「訂正・改善案」に目を通し、教材を良くするものは会話の文体（語尾・キャラクター）と再発見サイクルの構造を壊さない範囲で反映する**（案は素材であり、そのまま貼らず台詞になじませる。採否と内容を報告に記録する）。
   - **裏付けあり** → 該当文の直後に `[^N]` を付ける。発言外枠の閉じカギカッコは追加しない。
   - **矛盾（誤り）** → 訂正案を下敷きに最小限の修正を行い、修正後の記述に脚注を付ける。
   - **確認できない** → ソースを捏造しない。「〜と言われている」への弱め方や削除を検討し、判断が難しければ報告で保留として挙げる。
6. **既存の Wikipedia 脚注の格上げ。** `grep -n 'wikipedia\.org' <file>` で洗い出し、重要なものだけ第3段を実行する。ここでもフォールバック禁止。

### 脚注を書くとき

書式は `citation.md`（正本）に従う。校正固有の要点は次の3つ。

- 各脚注定義に、本文に呼応した簡単な解説を添える。検証で得た `title` や `extract` をそのまま貼らず、本文の文脈に合わせて要約する。
- 第3段で一次資料を出典にした場合、サイト名＝出版元・機関（arXiv、Physical Review、CERN など）、ページタイトル＝一次資料の正式タイトル、URL＝第3段(2) で確認済みのもの。
- フォールバックで Wikipedia 止まりになった主張は Wikipedia を出典にする。

## 処理2: 文章の流れ・論理展開の検証

処理1（事実）と処理3（数式）が個々の正しさを見るのに対し、ここは**つながり**を見る。数式検証より先に行うのは、流れの修正で台詞を補ったり動かしたりした後に数式・数値を最終検証したいから（構造を先に確定させる）。幕順に通読し、次を確認する。

1. **論理の飛躍・ステップ抜け**：やらない夫の説明が段を飛ばしていないか。やる夫が、直前に提示されていない情報でいきなり「わかった」ことになっていないか。抜けたステップは既存の文体で一言補う。
2. **前後の依存関係**：概念・記号・結論を導入前に使っていないか（前方参照）。既出のものを未出のように再定義していないか。幕をまたぐ参照（「第N幕でやった〜」）が実際の内容と対応しているか。
3. **会話の噛み合わせ**：やる夫の疑問にやらない夫の応答が噛み合っているか。投げた疑問が回収されず放置されていないか。「あとで説明する」と予告した事項が実際に回収されているか。
4. **話題の断絶・重複**：唐突な話題転換で読者が置き去りにならないか。同じ説明が離れた場所で不要に重複していないか（意図的な復習は除く）。
5. **再発見サイクルの健全性**：素朴案→反例→修正が途中で切れていないか（反例なしに結論だけ来ていないか、素朴案が潰されず放置されていないか）。これは構造の検証であって、意図された誤り自体は直さない。

修正は最小限。**再発見サイクルの構造・キャラクターの文体・語尾を壊さない。** 大きな入れ替えや加筆が必要と判断したら断行せず、報告で提案する（読者体験に関わる構成変更はユーザー判断）。

## 処理2.5: 専門用語の英語併記

処理2で用語の登場順が確定した後、幕順に一度だけ通す。**専門用語（学術用語・概念名・物質名・手法名）には、本文での初出1回だけ全角括弧で英語を併記する。** 書式の正本は `.claude/skills/yaruo-rediscovery/references/format.md` の「専門用語の英語併記」。

1. 幕ごとに新出の専門用語を拾い、併記の有無を確かめる。**幕・節のタイトルには付けない**（見出しは日本語のまま）。
2. 併記が2回目以降の位置にあれば初出へ移す。台詞に既に英語綴りがあるなら重ねない（`エングラム、engram。` → `エングラム（engram）だ。`）。
3. 一般語・比喩用法へ付けない。同じ語でも比喩で先に出ている場合は、専門用語として使われる箇所が初出。
4. 訳語が複数ある語は教材内で一つに統一する。略語は `（long-term potentiation）` の直後の台詞で「略して LTP だ」と導入するか、`（long-term potentiation, LTP）` と書く。
5. 機械検査は `python3 scripts/yaruo_lint.py <file> --check --rules term-english`。初出でない位置・重複・半角括弧が warning に出る。**どの語に併記すべきかは検出できない**ので、そこはこの処理で人が拾う。

## 処理3: 数式と会話の整合性検証

処理2で流れが確定した後に行う。幕ごとに全数式（`$$...$$` と台詞中の `$...$`）を抽出し、次を確認する。

1. **式単体の正しさ**：係数・符号・添字・次元（単位）。標準的な教科書の形と一致するか。
2. **式変形の連鎖**：前の式から次の式が本当に導けるか。省略されたステップを自分で埋める。手計算で追えないものは Python（sympy / numpy）で検算する。
3. **会話と式の一致**：台詞の内容と直後の式が一致しているか。**数値例は必ず実際に計算して確かめる**（このスキルの検出力が最も高いのはここ。「62,800 km のはずが〜」型の具体的数値は全部再計算する）。処理2で補った箇所に数値・式が混じっていたら、それも必ず検算する。
4. **記号の一貫性**：同じ量にファイル全体で同じ記号が使われているか。途中で定義なく変わっていないか。

修正対象は (a) 正解として提示された式の誤り、(b) 「わざと間違えたはずの式」が実は間違っておらず反例が成立していない場合、(c) 会話が式の内容を誤って説明している場合。

検算スクリプトはスクラッチパッドに書き、削除せず残す。

## 完了報告

- ファクトチェック：検証した主張の数／付与した脚注の数／**修正した記述の一覧（修正前→修正後）**／改善案を採用しなかった主張とその理由／保留にした主張
- 流れ・論理展開：見つけた問題の数／**修正した箇所の一覧**／自分で直さず構成変更として提案した項目
- 用語の英語併記：新たに併記した用語の一覧／移動・削除した併記／`term-english` の warning のうち意図どおりとして残したもの
- 数式検証：検証した式の数／**修正した式の一覧（根拠つき）**／検算スクリプトの場所

修正が1件もない処理についても「検証した上で問題なし」と明示する（やっていないのと区別がつくように）。

## チェックリスト

- [ ] 記載した URL はすべて curl / WebFetch で実在確認済みか
- [ ] 一次資料の脚注は第3段(2) で開いて裏付けを確認済みか（失敗したら Wikipedia 出典に戻したか）
- [ ] 参照日は作業当日か、脚注番号は通し番号で重複・欠番がないか
- [ ] 再発見サイクルの「意図された誤り」を訂正していないか
- [ ] 修正した台詞はキャラクターの語尾・文体を維持しているか
- [ ] 専門用語の英語併記は初出1回だけか、見出しに付けていないか
- [ ] 具体的数値の登場箇所をすべて再計算したか
- [ ] 修正一覧を修正前→修正後の形で報告したか
