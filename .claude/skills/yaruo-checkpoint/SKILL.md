# Learning Checkpoint を作る

本文は改訂され続ける。だから **「何幕まで読んだ」を学習成果の正本にしない。** 正本は概念にする。

教材ごとに `docs/books/{ID}/checkpoints.yml` を置き、次の3つを対にして記録する。

| 要素 | 何を書くか |
|---|---|
| `statement` | 読者が到達したときに**できること**（「〜を説明できる」で閉じる） |
| `evidence` | その概念が本文で実際に扱われている証拠（本文からそのまま引く断片） |
| `probes` | 読了直後・翌日・数日後に出し直す想起練習 |

書式・個数・語彙の正本は `scripts/checkpoints.py`。**規約をここへ複製しない。**

```bash
python3 scripts/checkpoints.py docs/books/<id>/checkpoints.yml --check --verbose
python3 scripts/checkpoints.py --scaffold <id> > docs/books/<id>/checkpoints.yml
```

## いつ作るか

- 教材が完成した直後（`yaruo-rediscovery` の納品後）。
- 受け入れレビュー（`yaruo-review`）で、教材が実際に到達させる概念を確かめるとき。
- 大幅改訂の後。**このとき id を振り直さない**（下記）。

## 手順

### Step 1: 問いから到達行動を引く

`catalog.yml` の `question` を読み、**その問いに答えられる人は何を説明できるか**を先に書き出す。本文の見出しを写して checkpoint にしない。見出しは構成の都合で並んでおり、到達行動とは一致しない。

### Step 2: 粒度を決める

有効な checkpoint は 5〜15。多くなるなら粒度が細かすぎる。次で判断する。

- **核心概念は checkpoint になる。** 教材が再発見サイクルを回した概念。
- **補助用語は checkpoint にしない。** 名前を覚えているかは到達行動ではない。
- **一つの statement に到達点を二つ入れない。** 「AとBを説明できる」は二つに割るか、両方を含む上位の説明へ言い換える。
- **教材の外へ持ち出せない到達点は落とす。** 「第3幕で誰が何を言ったか説明できる」は学習成果ではない。

`depends_on` に前提の checkpoint を書く。既知から未知へ到達する順序が壊れていれば、ここで循環として現れる。

### Step 3: 証拠を引く

各 checkpoint について、その概念が本文で扱われている一文を `evidence` へそのまま引く。**引けない checkpoint は、教材がまだ到達させていない。** 削るか、本文側の欠落として `yaruo-review` へ回す。

引用は本文が改訂されると消える。消えたときは error ではなく warning が出る。**概念ごと消えたのか、言い回しが変わっただけかを人が見て引き直す。** id は変えない。

### Step 4: 想起練習を設計する

`kind` は3種で、役割が違う。

| kind | 問うもの | 例 |
|---|---|---|
| 説明 | 機構を自分の言葉で言えるか | 「なぜ外から冷やしても熱が下がらないか」 |
| 予測 | 未知の条件で結果を先に言えるか | 「氷水に沈めると体温はその後どう動くか」 |
| 転移 | **教材に出てこない状況**へ当てられるか | 「エアコンが寒すぎるとき窓を開けるのは有効か」 |

`when` は `直後` / `翌日` / `数日後`。同じ問いを3回出すのではなく、間隔が延びるほど転移側へ寄せる。

**設問に答えを書かない。** `prompt` が `expected` をそのまま含むと error になるが、機械が見るのはそこだけで、遠回しな漏らし方は人が見る。`expected` は採点者が見る要点であり、読者には出さない（`--quiz` は既定で伏せる）。

### Step 5: 出題する

```bash
python3 scripts/checkpoints.py docs/books/<id>/checkpoints.yml --quiz 翌日
python3 scripts/checkpoints.py docs/books/<id>/checkpoints.yml --quiz 数日後 --with-expected
```

`--with-expected` は採点する側だけが使う。

## id を振り直さない

id は学習記録の宛先になる。番号を詰め直すと、過去の記録が別の概念を指してしまう。

- 概念が教材から消えたら、行を削らず `retired: true` を立てる。有効数の下限からは外れる。
- 統合したら、残す側の id を維持し、消える側を `retired` にする。
- **本文の版を checkpoints.yml へ記録しない。** 追うのは概念であって本文の版ではない。

## 他工程との関係

- **`yaruo-review`**：checkpoint は「教材が何を教えたつもりか」の宣言。レビューは、本文がそこへ到達させているか（6段表の空セル）を見る。宣言と本文が食い違ったら、直すのは原則として本文側。
- **`yaruo-rediscovery`**：新規執筆では Step 2（概念の分類）で checkpoint 候補を先に置ける。**候補は執筆前に固定しない**（再発見の過程で到達点は動く）。
- **モデルの使い分け**：初期候補の列挙は軽い工程、粒度の判断と転移問題の設計は重い工程。`MODELS.md` を見る。
