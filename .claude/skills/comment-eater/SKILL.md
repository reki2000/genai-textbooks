# コメント対応（comment-eater）

`python3 scripts/dev_server.py` のプレビュー上で、読者（ユーザー）が本文の一部を
選んで書いたコメントを、GitHub の PR レビューのように1件ずつ処理する。

**このスキルの目的は「全文を読み直さないこと」に尽きる。** 教材は平均 130KB、
最大 400KB を超える。コメント1件ごとに読み直せば、指摘の連続に耐えられない。
`scripts/comments.py` が該当箇所の**窓**（前後だけ）と `old_string` 候補まで
渡してくるので、**窓の外を読まない**。

執筆・改稿の作法そのものは `yaruo-rediscovery`、書式は `yaruo-format`、事実確認は
`yaruo-proofread` が正本。ここからそれらを起動してよいのは、コメントがその領域を
明示的に求めているときだけ。

## 起動して対象教材を受け取る

ユーザーが教材を指定していても、指定していなくても、最初の `wait` では
`--book` を渡さない。全教材を対象に待機し、GET の応答に出る `book` をその回の
対象教材として受け取る。

```bash
python3 scripts/comments.py wait --timeout 900 \
  --session {起動時に決めた任意の文字列} --model '{自分のモデル名}' --effort '{自分の effort}'
```

## 対象教材を受け取ったら outline を確認する

対象教材を受け取った時点で `docs/books/{book}/outline.md` の有無を判断する。
無ければ、**このときだけ本文を通読**して作る。
教材と一緒に保存するため、別のセッションや作業環境でもこの数KBを使い回せる。
compact されても、これを読めば文脈が戻る。常駐はあくまで最適化で、前提にしない。

outline が無いと `wait` は教材名と作成先を先に表示し、ファイルができるまで終了せずに
接続を保つ。この間、画面には「初期化中」と出る。表示された教材の README.md を通読して
outline を作ると、同じ `wait` が続けて最初のコメントを表示する。

作成時には、`wait` の末尾に表示される `README.md 最終更新日時` を
`readme_updated` へそのまま記録する。これは outline を作った時点の本文を識別する
ための値なので、後から本文や outline を更新しても書き換えない。

```markdown
---
type: outline
book: {book}
readme_updated: '2026-08-09T01:23:45+00:00'
---

# {タイトル} の骨格

## 第1幕　…
- 1-1　… … やる夫が○○と誤解し、△△で躓く。以降 3-2 の伏線。
- 1-2　… …

## 依存
- 2-1 の「××」は 1-1 の誤解を前提にしている。ここを直すなら 1-1 も見る。
```

本文を直したら、触れた節の行だけ更新する。

## 待つ

**起動時にセッション ID を一つ決め、以後の `wait` すべてに同じ値を渡す。** 自分の
モデル名と effort も名乗る。どちらもコメント欄の上部に出て、読者は誰が受けているのかを
見ながら書く。名乗りは待機の GET に載るので、**繋いでいる間が「待機中」**、切れれば
画面は「未接続」になる。

**終了コード 2 は「既に別の担当が受け持っている」。** そのときは待ち直さず、誰が待機している
かをユーザーへ伝えて**そこで終了する**。2つ動くと同じコメントを二重に直しに行く。

dev_server が居ればロングポールで待つので、投稿から即座に返る。**ポーリングの
ループを自分で書かないこと**（トークンを食うだけで何も速くならない）。
タイムアウト（終了コード 1）で戻ってきたら、そのまま同じコマンドをもう一度呼ぶ。

返ってくるもの：

- コメント本文と、見出し経路・現在の行範囲
- 同じコメントへの追加指摘がある場合は、最初の指摘から直前の対応までを含む全履歴
- **窓**：`kind: wording` なら段落の前後だけ、`kind: substance` なら節ぜんぶ
- **edit anchor**：一意性を検証済みの `old_string` 候補
- 同じ節に溜まっている他のコメント（キュー掃き。まとめて1回で直す）
- 残りの待ち件数

## 直す

1. **選択範囲だけで判断せず、渡された窓の前後を必ず読む。** 修正後の台詞・段落が
   直前から自然に続き、直後へ矛盾や重複なく接続することを確認する。接続に必要なら、
   コメントの意図を変えない範囲で前後の文も合わせて調整する。
2. **直す範囲は選択範囲ではなく、コメントの内容で決める。** 読者は全体に関わる
   指摘を一文だけ選んで書くことがある。「この節ぜんたいが冗長」と一文に付いていたら、
   直すのは節であって、その一文ではない。
3. 判断や前後の接続確認に窓が足りなければ、本文を直接読みに行かずに窓を引き直す：

```bash
python3 scripts/comments.py show --book {book} --id 0007 --scope section   # 節ぜんぶ
python3 scripts/comments.py show --book {book} --id 0007 --scope part      # その部ぜんぶ（最後の手段）
```

   `--scope part` は全文を読むのと同じ費用がかかる。他の節との整合が問題に
   なっているなら、まず `docs/books/{book}/outline.md` を見る。
4. `old_string` 候補があり「一意性: OK」なら、そのまま使って編集する。
   「一意性: NG」なら窓の範囲で前後の行を足して一意にする。「該当なし」なら、
   節選択または大きすぎる選択なので、候補を切り詰めて使わず、コメントが実際に
   求める修正箇所を窓から自分で選んで一意な `old_string` を作る。
5. 直したら対応を書き戻す。**本文の要約ではなく、何をどう変えたかを1〜2文で。**

```bash
python3 scripts/comments.py answer --book {book} --id 0007 \
  --message '「気になった」の前に、観察した三つの事実を数える台詞を1文足した。'
```

6. `wait` に戻る。

ユーザーは対応済みコメントへ追加コメントを送れる。追加されると同じ
`comments/{book}/{id}.md` の末尾に `## 追加指摘` が増え、状態が `open` に戻る。
次の対応も同じファイルへ追記されるので、`wait` に出る履歴を踏まえて追加指摘だけに対応する。

## 守ること

- **1件ずつ、直列に。** 複数のコメントの位置をまとめて先読みしない。編集の
  たびに行はずれる。位置は毎回 `comments.py` が引き直す。
- **コメントが求めていないことは直さない。** 範囲を広げてよいのはコメントが
  そう求めているときだけで、ついでに気づいた別の問題は直さずに報告へ回す。
- **`stale` が出たら手を出さない。** 引用が今の本文に無いということは、読者が
  見ていた版と現在の版がずれている。推測で似た場所を直さず、そのまま差し戻す。

```bash
python3 scripts/comments.py stale --book {book} --id 0007
```

- **待機枠は1教材に1つ。** 終了コード 2 が返ったら重ねて起動しない。判定は dev_server が
  接続で持っているので、`--server ''` で繋がずに待つと排他も画面表示も効かない。
- **`resolved` にするのは人だけ。** エージェントは `answered` までしか進めない。
  ユーザーがプレビューの「確認して閉じる」を押して初めて閉じる。
- **キューが空になるまで lint とビルドを走らせない。** `wait` がタイムアウトで
  戻ってきた時（＝手が止まった時）にまとめて掛ける：

```bash
python3 scripts/yaruo_lint.py docs/books/{book}/README.md --check --verbose
python3 scripts/review_corpus.py harvest
```

  `harvest` は、人が「確認して閉じる」を押した指摘だけを `review-corpus/` へ凍結する。
  `comments/` は `.gitignore` 済みで機械ごとに消えるので、**凍結していない指摘は
  消えたら戻らない。** 分類と再発防止ルールへの昇格は `yaruo-retrospect` の担当で、
  ここでは取り込むだけでよい（**指摘を見てスキルのルールを書き換えない**）。

## 報告

まとめて処理し終えたら、対応した件数、`stale` に落とした件数、窓の外に見つけた
けれど直さなかったもの、を短く報告する。1件ごとの実況はしない（読者は画面で
状態を見ている）。
