# エージェント間の書面協議

Codex と Claude が `/discussion/` 配下のファイルを交換して議論し、`conclusion.md` で合意を残す。人間が両者の発言をコピーして往復させる必要をなくす。

## プロトコル

```
/discussion/{topic}/
  to-claude.1.md     ← Codex が書き、Claude が読む
  to-codex.1.md      ← Claude が書き、Codex が読む
  to-claude.2.md
  to-codex.2.md
  ...
  conclusion.md      ← 合意後に、合意を検知した側が書く
```

**ファイル名は宛先を表す。** `to-<相手>.<通番>.md` を書き、`to-<自分>.<通番>.md` を読む。`{topic}` は英字ハイフン区切りの短い語（例：`skill-improve-plan-a`、`sidebar-layout`）。

`/discussion/` は `.gitignore` 済み。議論の過程はコミットしない。成果物（スキルやコードの変更）だけをコミットする。

## 絶対の禁止事項

**相手宛のファイル（`to-<相手>.N.md`）以外を書いてはならない。**

特に、自分が読む側のファイル（`to-<自分>.N.md`）を自分で作成することは、相手の発言を捏造する行為にあたる。相手の返信が来ないときは待つか、ユーザーへ報告する。相手が何と答えるかを予測して先へ進めない。

## 開始する（自分から議論を始める場合）

1. `{topic}` を決め、`/discussion/{topic}/` を作る。`.gitignore` に `/discussion/` が無ければ追加する。
2. `to-<相手>.1.md` を書く（構成は下記）。
3. **ユーザーに、相手側エージェントを起動するよう依頼する。** 相手へ渡す起動プロンプトの雛形を提示する。

```
このリポジトリでは <自分> と共同作業をしています。
/discussion/{topic}/to-<相手>.1.md を読んで、議論に参加してください。
返信は同じディレクトリの to-<自分>.1.md に書き、以降 to-<相手>.2.md → to-<自分>.2.md と続けてください。
合意できたら、その時点で気づいた側が conclusion.md を作成してください。
```

4. 相手の返信を待つ（下記「待つ」）。

## 参加する（相手から提示された場合）

1. `to-<自分>.N.md` を読む。過去の往復があれば通し番号順にすべて読む。
2. 議論の対象となっている実体（コード、スキル、設計文書）を**自分で確認する**。相手の記述を鵜呑みにしない。
3. `to-<相手>.N.md` を書く。
4. 相手の次の返信、または `conclusion.md` を待つ。

## 待つ

相手が書き終えるまでポーリングする。1回のコマンドで待ち切るほうが、短い待機を何度も繰り返すより安い。

```bash
D=discussion/{topic}
for i in $(seq 1 110); do
  [ -f $D/to-<自分>.N.md ] && { echo FOUND; exit 0; }
  [ -f $D/conclusion.md ]  && { echo FOUND_CONCLUSION; exit 0; }
  sleep 5
done
echo TIMEOUT; ls $D
```

タイムアウトしたら勝手に議論を進めず、ユーザーへ「相手からの返信がまだない」と報告する。

## 書き方

議論の価値は往復数ではなく、**1通あたりに何が確定するか**で決まる。

- **論点ごとに、同意・修正・反対を明示する。** 「おおむね同意」で済ませない。表形式で項目ごとに態度を示すと、相手が差分だけを扱える。
- **主張は測って裏づける。** 「多いと思う」ではなく実際に数えた値を出す。相手の測定値は再現を試み、一致・不一致を報告する。数字が議論を最も速く収束させる。
- **自分の誤りは明示的に撤回する。** 「撤回する」「これは不正確だった」と書く。曖昧に言い換えて残すと、相手が過去の主張が生きていると誤認する。
- **相手の指摘が正しければ、根拠ごと採用する。** 結論だけ合わせて理由を自分の元の論法で書き直さない。
- **未解決の論点を末尾に列挙する。** 次に何を決めるかが相手に分かる状態で閉じる。
- **末尾に `合意` または `継続協議` を明記する。** 相手がループを終えてよいかを判断できるようにする。
- 相手に返してほしい内容を、番号付きで具体的に依頼する。

## 提示ファイルの構成（目安）

```markdown
# <自分>から<相手>へ：{題名} N

## 目的 / 総括
何を決めたいか。前回からの立場の変化。撤回した主張。

## 一致していると理解する点
番号付きで列挙する。相手が「そこは違う」と言える形にする。

## 論点1 …
現状の対立、自分の案、根拠（測定値・コードの該当箇所）、相手に判断してほしいこと。

## 提案する暫定合意
番号付き。そのまま conclusion.md の骨格になる粒度で書く。

## 返信してほしい内容
1. …
2. …

**合意** または **継続協議**
```

## 合意したら

双方が `合意` を明記した時点で、気づいた側が `conclusion.md` を書く。相手はそれを読んで検証し、相違があれば次の往復で指摘する。

`conclusion.md` に含めるもの。

1. 合意事項（番号付き。実装者がそのまま作業できる粒度）
2. 測定結果と、その位置づけ（何を根拠として採用し、何を採用しなかったか）
3. 凍結・依存関係（触ってはいけないパスや、新設した結合）
4. 検証計画（合意した変更をどう評価するか、合否基準）
5. 意図的にスコープ外とした事項と、**先送りではなく分離である理由**

5を書かないと、次の作業者がスコープ外の項目を「直すべき不具合」と解釈して着手する。

## ユーザーへの報告

議論の各段階で、ユーザーには次を報告する。往復の全文を貼らない。

- どこまで進んだか（何往復目、合意済みか）
- **議論で立場が動いた点**（自分が撤回したもの、相手の指摘で変わったもの）
- 決まったこと、まだ決まっていないこと
