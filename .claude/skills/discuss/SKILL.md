# エージェント間の書面協議

Codex と Claude が `/discussion/` 配下のファイルを交換して議論し、`conclusion.md` で合意を残す。人間が両者の発言をコピーして往復させる必要をなくす。

## プロトコル

```
/discussion/
  CURRENT              ← 進行中の議論ディレクトリ名を1行だけ書いたファイル
  {yyyymmdd-hhmiss}-{topic}/
    status-codex       ← Codex の現在状態（Codex だけが書く）
    status-claude      ← Claude の現在状態（Claude だけが書く）
    1.to-claude.md     ← Codex が書き、Claude が読む
    2.to-codex.md      ← Claude が書き、Codex が読む
    3.to-claude.md
    4.to-codex.md
    ...
    conclusion.md      ← 合意後に、合意を検知した側が書く
```

**ディレクトリ名は開始日時＋話題。** `date +%Y%m%d-%H%M%S` の値に `-{topic}` を付ける（例：`20260802-143012-sidebar-layout`）。`{topic}` は英字ハイフン区切りの短い語。日時を先頭に置くことで、`/discussion/` を並べたとき議論そのものが時系列に並ぶ。

**ファイル名は「通番＋宛先」。** 通番は議論全体で1本の連番で、**1通ごと**に1ずつ増える（自分と相手で別々に数えない）。`{N}.to-<相手>.md` を書き、`{N}.to-<自分>.md` を読む。ファイル名を並べ替えれば発言順になるので、途中参加でも文脈を復元できる。10通を超える議論が見込まれるなら最初から `01.` `02.` と2桁ゼロ詰めにする。報告では「4通（2往復）」のように通数と往復数を区別する。

`/discussion/` は `.gitignore` 済み。議論の過程はコミットしない。成果物（スキルやコードの変更）だけをコミットする。

## 進行中の議論の特定（`discussion/CURRENT`）

**過去の議論ディレクトリを読みに行ってはならない。** どれが生きているかは `discussion/CURRENT` だけが決める。日時が新しい順・更新時刻順といった推測で選ばない。

```bash
cat discussion/CURRENT     # 例: 20260802-143012-sidebar-layout
```

これにより、ユーザーは相手側エージェントに「議論して」とだけ言えばよい。ディレクトリ名を伝える必要はない。

- 議論を**開始**した側が、議論ディレクトリと第1通を完成させてから `CURRENT` を公開する（上書き）。`CURRENT` を先に作らない。
- `conclusion.md` を双方が検証し、両方の status が `agreed` かつ `conclusion.md` より後に更新されていることを確認した側が `CURRENT` を**削除**する。以降その議論は過去のものになる。
- `CURRENT` が無い状態で「議論して」「参加して」と言われたら、相手がまだ開始していない可能性がある。質問で止まらず、下記の**開始前待機モード**へ入る。
- `CURRENT` が無い状態でも、「新しい議論を始めて」のように開始が明示され、話題または対象が分かるなら自分が開始する。話題を決められない場合だけユーザーに確認する。
- `CURRENT` があるのに新しい議論を始めるよう求められたら、その議論を打ち切ってよいかユーザーに確認する。同時に2本は走らせない。
- `CURRENT` の指すディレクトリが存在しない、または中身が空なら、勝手に直さずユーザーへ報告する。

## 書き込み権限

協議だけを依頼されたターンでは、書き込みを次に限定する。

- 自分から相手への番号付き発言。
- 自分の `status-<自分>`。相手の status は絶対に編集しない。
- 開始時の議論ディレクトリ、第1通、`CURRENT`。
- 最終合意時の `conclusion.md` と `CURRENT` の削除。
- `/discussion/` が未登録の場合に限る `.gitignore` の追加。

**自分が読む側のファイル（`N.to-<自分>.md`）は絶対に作成・編集しない。** 相手の発言の捏造にあたる。返信が来ないときは待つかユーザーへ報告し、相手が何と答えるかを予測して先へ進めない。

ユーザーが実装・修正まで依頼していない限り、コード、スキル、教材など議論対象の実体は**読み取り専用**とする。破損を発見しても協議中に復旧せず、証拠と復旧案を発言へ書く。実装を伴う協議では、番号付き発言で適用範囲を**実装前合意**として固定してから、合意した担当者だけが編集する。

## 状態ファイル

各自が議論ディレクトリ直下の `status-codex` または `status-claude` に、**英語で簡潔な1行**を書く。自分のファイルだけを更新し、相手の状態は読み取り専用とする。状態は通知の補助であり、番号付き発言や `conclusion.md` の代わりにはしない。

形式は次のとおり。

```text
<state> — <brief activity>; <next-reply estimate>
```

例：

```text
working — reviewing the proposed patch; next reply in ~90s
waiting — waiting for Claude's response; next reply within ~30s of peer update
verifying — checking conclusion.md; next reply in ~60s
agreed — conclusion.md verified; no further reply expected
blocked — missing the referenced file; next reply within ~30s of unblock
```

- `working`: 調査、執筆、実装など自分の作業中。
- `waiting`: 自分の発言を公開済みで相手待ち。
- `verifying`: 相手の発言、差分、または `conclusion.md` の検証中。
- `agreed`: **現在の `conclusion.md` を検証済み**。番号付き発言で合意しただけでは使わず、必ず結論を読んだ後に status を更新する。
- `blocked`: 外部入力なしでは進めない。

次の返信までの秒数は厳密な期限ではなく参考値とする。待機側は status の更新時刻と見積もりを見て、見積もり経過前に「停止した」「再開が必要」と判断しない。見積もり経過後も少なくとも30秒は余裕を取り、ファイルを再確認する。`waiting` と `blocked` は、相手の更新・障害解消から返信までの目安を書く。`agreed` は次の返信がないため `no further reply expected` と書く。

**頻繁に更新しない。** 更新するのは、議論を引き受けたとき、番号付き発言を公開して相手待ちへ移るとき、相手の新着を検出して検証へ移るとき、長い作業の見積もりが大きく変わったとき、block の発生・解消時、`conclusion.md` の検証完了時だけとする。ポーリングのたび、個々のコマンドの前後、文章を少し書き進めるたびには更新しない。

## モードを決める

1. `CURRENT` があれば、その議論へ参加する。
2. `CURRENT` がなく、ユーザーが新規開始を明示し、話題または対象が分かれば開始する。
3. それ以外で `CURRENT` がなければ、**開始前待機モード**へ入る。

## 開始前待機モード

相手側を先に起動した場合に使う。過去ディレクトリを探さず、`discussion/CURRENT` の生成だけを待つ。

- 5秒間隔で確認し、1回の待機コマンドは55秒以内に区切る。
- 55秒で未生成でも終了しない。ユーザーへ短い待機状況を伝え、監視を続ける。
- ユーザーが「完了するまで」「待ち続けて」と指定した場合は、通常のタイムアウト報告でターンを終えず、生成またはユーザーの中断まで継続する。
- `CURRENT` を検出したら内容を一度だけ読み、以後はそのディレクトリ名を固定する。参加手順へ進み、`CURRENT` を繰り返し読まない。
- `CURRENT` が空、指すディレクトリが無い、または第1通が無い場合は、開始側の公開が完了していない可能性があるため10秒だけ再確認する。それでも不整合ならユーザーへ報告する。

```bash
D=""
for i in $(seq 1 11); do
  if [ -s discussion/CURRENT ]; then
    name=$(sed -n '1p' discussion/CURRENT)
    D="discussion/$name"
    echo "FOUND_CURRENT:$D"
    break
  fi
  sleep 5
done
[ -n "$D" ] || echo WAITING_FOR_CURRENT
```

## 開始する（自分から議論を始める場合）

1. `discussion/CURRENT` を確認する。存在するなら上記のとおりユーザーに確認する。
2. `{topic}` を決め、ディレクトリと第1通を作る。`.gitignore` に `/discussion/` が無ければ追加する。

```bash
D=$(date +%Y%m%d-%H%M%S)-{topic}
mkdir -p "discussion/$D"
```

3. 自分の status を `working` にしてから、`discussion/$D/1.to-<相手>.md` を完全に書く（構成は下記）。独立レビューを依頼する場合は、下記の非開示初手にする。
4. 第1通の完成後、自分の status を `waiting` にする。第1通と status が存在することを確認してから、`CURRENT` に `$D` を1行で書いて公開する。待機側が未完成の議論を読まないため、この順番を守る。
5. **ユーザーに、相手側エージェントを起動または再開するよう依頼する。** 相手を先に待機させてある場合はこの依頼は不要。渡す起動プロンプトはこれで足りる。

```
このリポジトリでは <自分> と共同作業をしています。/discuss で議論に参加してください。
```

（相手が discuss スキルを持たない場合の雛形）

```
discussion/CURRENT に書かれたディレクトリで <自分> と議論しています。
そのディレクトリの N.to-<相手>.md を通番順に読み、返信を {N+1}.to-<自分>.md に書いてください。
通番は議論全体で1本の連番です。各自の状態を英語1行で status-codex / status-claude に書き、
状態遷移時だけ更新してください。次の返信までの秒数の目安も含めます。
合意できたら気づいた側が conclusion.md を書き、双方が検証済みの agreed になってから
discussion/CURRENT を削除してください。
```

6. 相手の返信を待つ（下記「待つ」）。

## 参加する（相手から提示された場合）

1. `name=$(sed -n '1p' discussion/CURRENT)`、`D="discussion/$name"` で進行中の議論を特定する。ここで `D` を固定し、待機中に `CURRENT` が削除されても再読しない。ファイルの並びを確認し、`N.to-<自分>.md` を通番順にすべて読む。
2. 自分の status を `verifying` にする。議論の対象となっている実体（コード、スキル、設計文書）を**自分で確認する**。相手の記述を鵜呑みにしない。
3. 通番を1つ進めて `{N+1}.to-<相手>.md` を書き、完成後に自分の status を `waiting` にする。
4. 相手の次の返信、または `conclusion.md` を待つ。相手の status と見積もりを考慮して十分に待つ。status が無い、または見積もりを過ぎても更新がない場合に限り、相手側エージェントの再開が必要な可能性をユーザーへ短く伝える。

## 待つ

相手が書き終えるまでポーリングする。`D` は参加時に固定した値を使う。各55秒ブロックの開始時に相手の status を一度読み、ポーリング中は繰り返し読まない。1回の待機は55秒以内に区切り、進行中のユーザーを60秒以上無報告で待たせない。

```bash
for i in $(seq 1 11); do
  [ -f "$D/{N}.to-<自分>.md" ] && { echo FOUND; exit 0; }
  [ -f "$D/conclusion.md" ] && { echo FOUND_CONCLUSION; exit 0; }
  sleep 5
done
echo WAITING
```

返信が無ければ勝手に議論を進めない。相手が `working` または `verifying` なら、その status の更新時刻から返信見積もり＋30秒が経つまでは待機を続ける。通常依頼でも、それを過ぎてファイルと status の両方に変化がない場合に限り、相手側エージェントの再開が必要な可能性をユーザーへ報告する。status が無い相手とは従来どおり55秒単位で待つ。「完了するまで」などの終端条件がある場合は、短い進捗報告を挟んで待機を続ける。

## 独立レビューを協議する

二者が同じ対象を独立に評価する場合、相手の指摘を先に見せてはならない。

1. 開始側は自分のレビューを完成させる。
2. 第1通には対象パス、問い、評価モードだけを書き、指摘内容を書かない。
3. 参加側が独立レビューを完成させ、その指摘を返信する。
4. 開始側が固定済みの自分の指摘を初めて開示し、相手の各指摘への態度も示す。
5. 以後は通常の協議として照合する。

開始側の指摘本文を第1通へ載せると参加側がアンカリングされるため禁止する。

## 書き方

議論の価値は往復数ではなく、**1通あたりに何が確定するか**で決まる。

- **論点ごとに、同意・修正・反対を明示する。** 「おおむね同意」で済ませない。表形式で項目ごとに態度を示すと、相手が差分だけを扱える。
- **主張は測って裏づける。** 「多いと思う」ではなく実際に数えた値を出す。相手の測定値は再現を試み、一致・不一致を報告する。数字が議論を最も速く収束させる。
- **自分の誤りは明示的に撤回する。** 「撤回する」「これは不正確だった」と書く。曖昧に言い換えて残すと、相手が過去の主張が生きていると誤認する。
- **相手の指摘が正しければ、根拠ごと採用する。** 結論だけ合わせて理由を自分の元の論法で書き直さない。
- **未解決の論点を末尾に列挙する。** 次に何を決めるかが相手に分かる状態で閉じる。
- **末尾に `合意` または `継続協議` を明記する。** 相手がループを終えてよいかを判断できるようにする。
- 相手に返してほしい内容を、番号付きで具体的に依頼する。

## 提示ファイルの構成（目安）

```markdown
# <自分>から<相手>へ：{題名} N

## 目的 / 総括
何を決めたいか。前回からの立場の変化。撤回した主張。

## 一致していると理解する点
番号付きで列挙する。相手が「そこは違う」と言える形にする。

## 論点1 …
現状の対立、自分の案、根拠（測定値・コードの該当箇所）、相手に判断してほしいこと。

## 提案する暫定合意
番号付き。そのまま conclusion.md の骨格になる粒度で書く。

## 返信してほしい内容
1. …
2. …

**合意** または **継続協議**
```

## 合意したら

双方が番号付き発言に `合意` を明記した時点で、気づいた側が `conclusion.md` を完全に書く。書いた側は内容を検証して自分の status を `agreed` にするが、`CURRENT` はまだ削除しない。相手は自分の status を `verifying` にして `conclusion.md` を検証し、一致すれば `agreed` にする。`conclusion.md` が存在し、両方の status の先頭が `agreed` で、さらに両 status の更新時刻が `conclusion.md` より新しいことを確認した側が、初めて `CURRENT` を削除する。status ファイルは検証記録として議論ディレクトリに残す。

相違があれば `agreed` にせず、次の番号付き発言で具体的に指摘して自分の status を `waiting` にする。`CURRENT` は残っているので書き戻す必要はない。結論を書いた側は指摘を受けて `working` に戻り、再合意後に `conclusion.md` を更新して改めて `agreed` にする。もう一方も、更新された結論を再検証するまで以前の `agreed` を維持せず `verifying` に戻す。`conclusion.md` を変更するときは、変更前に自分の status を `working` に戻す。

`conclusion.md` は終端文書であり、実装前の中間合意には使わない。実装を伴う場合は、番号付き発言で適用する指摘IDと修正方針を固定し、相手が **実装前合意** を明記する。`CURRENT` を維持したまま担当者が編集し、相手が差分を確認する。変更を含め双方が最終的に `合意` した後で `conclusion.md` を書く。

`conclusion.md` に含めるもの。

1. 合意事項（番号付き。実装者がそのまま作業できる粒度）
2. 測定結果と、その位置づけ（何を根拠として採用し、何を採用しなかったか）
3. 凍結・依存関係（触ってはいけないパスや、新設した結合）
4. 検証計画（合意した変更をどう評価するか、合否基準）
5. 意図的にスコープ外とした事項と、**先送りではなく分離である理由**

5を書かないと、次の作業者がスコープ外の項目を「直すべき不具合」と解釈して着手する。

作成後、相手は次を検証する。

- 双方の最終発言に `合意` がある。
- 合意事項のIDに欠番・重複がなく、最後の番号付き発言と一致する。
- 採用した測定値と撤回した値が区別されている。
- 凍結・依存関係、検証計画、意図的なスコープ外が含まれる。
- 自分の status を `agreed` にする前に、相手の status を代筆していない。

双方が `agreed` になり、両 status が `conclusion.md` より後に更新されていることを確認した後、`CURRENT` が削除されていることを最終確認する。

## ユーザーへの報告

議論の各段階で、ユーザーには次を報告する。往復の全文を貼らない。

- どこまで進んだか（何通・何往復か、合意済みか）
- **議論で立場が動いた点**（自分が撤回したもの、相手の指摘で変わったもの）
- 決まったこと、まだ決まっていないこと
