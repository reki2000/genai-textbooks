# レビューを資産にする（retrospect）

コメントを直して終わりにすると、同じ指摘を何度でも受ける。かといって **1件の指摘をそのままスキルのルールへ書き足してはいけない。** それを続けると `SKILL.md` が「一度指摘されたことの一覧」になり、執筆時に読み切れなくなる。

```
人間コメント → AI修正 → 人が resolved → review corpus
  → クラスタリング → ルール候補 → 人の承認 → lint / review / rediscovery へ昇格
```

数えられる部分（凍結・紐づけ・ゲート判定）は `scripts/review_corpus.py` が持つ。**判断（どれが同じ問題か、どこへ昇格させるか）だけをここで行う。**

## いつ走らせるか

- `comment-eater` のキューが空になり、待機がタイムアウトで戻ってきたとき。
- 未分類の記録が10件を超えたとき（`stats` で分かる）。
- ユーザーが「同じ指摘が続く」と言ったとき。

## Step 1: 凍結する

```bash
python3 scripts/review_corpus.py harvest
python3 scripts/review_corpus.py stats
```

取り込むのは **`resolved` だけ**。`answered` 止まりは「AI が直したと主張している」に過ぎず、人が確かめていない。`stale` も入らない。

`comments/` は `.gitignore` 済みで機械ごとに消える。`review-corpus/` は残る。**凍結していないコメントは、消えたら二度と戻らない。**

## Step 2: 束ねる

`list --unlabeled` の記録を読み、**症状で**束ねる。教材の話題で束ねない（「化学の教材で3件」は傾向ではない）。

束ねる判断は「**同じ執筆時の癖から出た指摘か**」。次は別のパターンとして扱う。

- 「答えを先に言っている」と「説明が長すぎる」──前者は学習の順序、後者は密度。
- 「反例が弱い」と「反例が無い」──後者は6段表の欠落、前者は素朴案の設計。

既存パターンに当てはまるなら紐づける。当てはまらないなら票を作る。

```bash
python3 scripts/review_corpus.py new-pattern answer-before-question
python3 scripts/review_corpus.py label cold-medicine/0007 answer-before-question
```

**一件しか実例が無いうちは、パターン票を作ってもよいが昇格させない。** 票は「まだ一般則ではない観察」を置く場所でもある。

## Step 3: 票を書く

必須の3節（`check` が見る）。

| 節 | 書くこと | 書かないこと |
|---|---|---|
| 症状 | 本文に何が起きているか。読者が何を見るか | 修正案 |
| なぜ学習上問題なのか | **どの理解が損なわれるか。** 「読みにくい」で止めない | 「面白くない」 |
| 推奨される修正 | 執筆時に何をすれば防げるか。修正時に何を足すか | 「〜しない」だけの禁止 |

「なぜ学習上問題なのか」を書けないパターンは、好みの問題である可能性が高い。`status: rejected` にして理由を残す。**却下も資産**で、同じ議論を繰り返さないための記録になる。

## Step 4: ゲートを通す

`check` が見るのは2つ。

- **発生3件以上、かつ2教材以上。** 1教材で3回は、その教材固有の癖かもしれない。
- **`approved_by` が空でない。** 人が承認していないものは昇格しない。エージェントがここを埋めない。

```bash
python3 scripts/review_corpus.py check
```

ゲートに到達したパターンは warning で「承認待ち」として出る。ユーザーへ、症状・実例・提案する昇格先を添えて承認を求める。

## Step 5: 昇格先を振り分ける

| 判定に要るもの | 昇格先 | 実装 |
|---|---|---|
| 行単位で機械判定できる | `scripts/yaruo_lint.py` | ルールを足し、`scripts/tests/fixtures/<ルールID>/` に input と expected を置く。`run_lint_tests.py` が通ること |
| 全文脈を読む判断が要る | `yaruo-review` | 観点1〜4のどれかへ、**証拠の取り方**として1行 |
| 執筆時に防ぐべき | `yaruo-rediscovery` | 症状が出たときだけ読む `anti-patterns.md` へ処方箋、毎回読む `section-card.md` へは本当に例外なく必要なものだけ |
| 到達目標の宣言と本文のずれ | `yaruo-checkpoint` | — |
| 図版の選定・作図 | `zuhan` | — |
| 事実・出典・数式 | `yaruo-proofread` | — |

迷ったら**執筆側へ寄せる**。レビューで捕まえるより、書くときに起きない方が安い。

昇格したら票へ記録する。

```yaml
status: promoted
approved_by: '（承認した人）'
promoted_to: 'rediscovery'      # または lint:<ルールID> / review / checkpoint / zuhan / proofread
```

## Step 6: 昇格の作法

**足した分だけ、畳めないか見る。** スキルは長くなるほど読まれなくなる。

1. 既存の項目へ1文で吸収できるなら、新しい節を作らない。
2. 新しい節を作るなら、**何をするか**（処方箋）で書く。禁止の羅列にしない。
3. 同じ規約を2つのスキルへ書かない。正本を1つ決めて、他方はそこを指す。
4. 昇格したルールが効いているかは、次の retrospect で見る。同じパターンの記録が止まっていなければ、ルールの置き場所か書き方が間違っている。

## 報告

- 凍結した件数と未分類の残り
- 新設・更新したパターンと、その実例数・教材数
- ゲートに到達し、承認を待っているパターン（症状・提案する昇格先つき）
- 昇格させたパターンと、実際に触ったファイル
- 却下したパターンと理由
