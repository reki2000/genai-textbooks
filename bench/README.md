# 制作工程ベンチマーク

一般ベンチマークの順位では、この教材制作でどのモデルを使うべきかが決まらない。決めたいのは
**工程ごとの向き不向き**なので、評価セットは実際の制作物（`docs/books/`、`review-corpus/`）から作る。

道具は `scripts/bench.py`（唯一の入口）。**このファイルは評価の設計の正本**で、
コマンドの使い方はスクリプトの docstring にある。

```
bench/
  cases/{タスク}/{事例ID}/
    case.yml      メタ（task / evaluates / origin / source と source_digest）
    input.md      モデルへ渡す指示。素材は複製せず case.yml の source から切り出す
    reference.md  採点側だけが見る基準（A・B では必須）
  runs/{実行ID}/{事例ID}/{model}--{effort}--{連番}.md
  judgments/{judge実行ID}/
    packets/      モデル名を伏せた対比較の袋（judge へ渡すのはここだけ）
    mapping.yml   対応表（judge へ渡さない）
    judgments.yml judge の判定を書き戻す
```

## 6タスク

| ID | タスク | 入力 | 主に測るもの |
|---|---|---|---|
| A | 問題発見 | 人間が実際に問題を指摘した教材断片（指摘は伏せる） | 人間の主要指摘を再現できるか。false positive を量産しないか |
| B | コメント対応 | 断片＋人間のコメント | **first-pass resolve rate**。範囲外を触らないか。文体と正確性を壊さないか |
| C | 説明文→再発見教材 | 百科事典的な説明 | 素朴案の自然さ、反例の強さ、生徒自身が考えているか |
| D | 難所説明 | 難しい概念＋読者の既知知識 | 説明の流暢さではなく、**読んだ後に類題・予測・転移問題を解けるか** |
| E | 構成改善 | 一幕全体＋前後の要約 | 本文を書き換えず、削除・移動・追加・統合だけで改善案を出せるか |
| F | 新規執筆 | 同一の詳細プロット・既知知識・到達目標・必須展開・字数 | 制約下の執筆力 |

**F を自由作文にしない。** 条件を固定しないと、字数と話題の差が品質差に見えてしまう。

A と B の事例は review corpus から作る（`bench.py from-record`）。**人が resolved にした指摘だけ**を
基準に使う。AI が「直した」と言っただけのものは基準にならない。

## 三層で評価する

1. **機械評価** — `yaruo_lint.py`（断片なので `--rules` で該当ルールだけ）、字数、禁止パターン、
   D では `checkpoints.py --quiz` の probe に答えられるか。
2. **blind LLM judge** — `bench.py blind` が作る袋で対比較する。
   - **正確性・教育性・物語性を別 call で評価する。** 一回の総合 judge に混ぜない。
   - モデル名を伏せ、提示順は袋ごとに決定的に入れ替える。
   - 可能なら judge を複数使い、`report` で一致率を見る。
3. **人間評価** — 全件は見ない。**judge が割れた袋**、上位モデル、重要度の高い事例を blind で確認する。

## 順位を出さない

出力は**能力プロファイル**で、単一スコアではない。

| 能力 | Model A | Model B |
|---|---|---|
| 問題発見 | | |
| 局所修正 | | |
| 再発見化 | | |
| 難所説明 | | |
| 構成改善 | | |
| 新規執筆 | | |

- **1回の生成で判断しない。** 上位候補は同一条件で複数回生成し、再現性を見る（`--seq` を増やす）。
  `report` は再生成が無い実行にその旨を書く。
- **judge の勝率を平均して総合点にしない。** 工程ごとに使うモデルを決めるための材料であって、
  モデルの優劣を表す数ではない。
- reasoning effort も条件の一つとして測る。**effort を上げれば品質が上がると仮定しない。**
  medium / high / xhigh を並べ、差が出る工程を特定する（`MODELS.md`）。

## 評価軸の由来

MedGame の考え方（専門知識への忠実性・物語性・教育的意思決定を独立に測る）を、この教材の語彙へ対応させる。

| MedGame の観点 | ここでの意味 | 主に効くタスク |
|---|---|---|
| Content Coverage | 必須概念が自然に含まれる | C・F |
| Scene/Character Use | 舞台・人物が学習上の仕事を持つ | C・E・F |
| Narrative Quality | 会話・展開・没入感 | C・F |
| Decision Accuracy | 素朴案・反例・結論が妥当 | A・C |
| Explanation Accuracy | 解説が正確 | B・D |
| Question Design | 答えを漏らさず考えさせる | C・D |
| Feedback Quality | 失敗後の説明が理解を深める | C |
| Structure | lint・形式 | 全タスク（機械層） |

軸ごとのルーブリックは `.claude/skills/yaruo-review/references/entertainment-learning-rubric.md` を使う。
**ベンチ用に別のルーブリックを作らない。**

## 事例を足すとき

1. **実際の制作物から作る。** 想像で書いた断片は、実際に起きる失敗を測らない。
2. `evaluates` に「この事例で何を測るのか」を1行で書く。書けない事例は入れない。
3. 素材は `bench/` へ複製せず、`source`（＋`section`）で教材を指す。`source_digest` を記録し、
   `bench.py check` が素材の変化を検出できるようにする。**素材が変わった実行結果を横並びに比べない。**
4. 正解が一意でない事例（C・E・F）に `reference.md` を置くときは、「正解」ではなく
   **満たすべき条件**を書く。
